## 一、系统边界

**包含什么**

- 文档上传与入库（txt / markdown）
- 检索与问答（带引用、带拒答）
- 权限过滤（知识库级 + 文档级 + 密级）
- 异步任务（解析 / 向量化）与任务状态查询
- 评估集运行与报告

**不包含什么**（对应 `spec.md` 第四节）

- PDF/Word/OCR 解析、多轮对话、文档在线编辑、
  GraphRAG 等高阶 RAG、SSO、K8s 部署

**外部依赖**

| 依赖 | 用途 | 是否必须 | 出问题时的降级方案 |
|------|------|---------|-----------------|
| 云端大模型 API | 生成答案 | 是 | ① 切换备用模型 ② 全局降级开关：只返回检索片段（不加生成） |
| 本地 bge-m3 推理服务 | 向量化 | 是 | 无法降级。入库会积压，问答会影响查询向量生成 → **必须做健康检查与重启策略** |
| 本地 bge-reranker | 重排（V1） | 否 | 直接跳过重排，用融合结果取 Top-5（指标约降 5%） |
| 内网共享盘 | 取原始文档 | 否（V1 后用上传替代） | 无 |

## 二、技术栈（硬约束，不得擅自更换）

> 选择标准：**对小白最友好 > 最容易部署 > 社区资料最多 > 预算内 > 满足数据合规**。
> 每一项都要写"换成别的会有什么麻烦"——这是防止你（或 AI）轻易动摇的关键。

| 层 | 选择 | 它是什么（大白话） | 为什么适合我 | 换成别的会有什么麻烦 |
|----|------|-----------------|------------|-------------------|
| 前端 | Next.js 15 + TS + Tailwind + shadcn/ui | 做网页的工具，组件都是现成的 | AI 最熟，出错时它能自己修；组件复制即用 | 换 Vue/Svelte 我要重学，AI 的资料也少 |
| 后端 | FastAPI + Pydantic v2 | Python 写接口的框架，自带接口文档 | 与 RAG 代码同语言；自动生成接口文档 | 换 Java/Go 我看不懂算法部分 |
| 关系库 | PostgreSQL 16 | 存结构化数据的数据库 | 元数据 + 权限 + 向量**同一个库**，能在一个查询里做过滤 | 拆成两个库就要自己保证一致性，单人做不到 |
| 向量存储 | pgvector（HNSW） | 让 PG 也能存和查向量 | 不引入新组件；权限过滤和向量检索在同一事务 | 用 Milvus/Chroma 就要跨库过滤 → 越权风险 + 数据同步难题 |
| 关键词检索 | PG 全文检索（`tsvector` + `pg_trgm`） | 按字词精确匹配 | 少装一个 ES；中文用 pg_trgm 兜底 | 装 ES 要多维护一个集群，单人负担过重 |
| 嵌入模型 | bge-m3（本地，1024 维） | 把文字转成向量的模型 | 中文好、数据不出内网、零调用费 | 云端 API 违反数据合规 |
| 重排序 | bge-reranker-v2-m3（本地） | 给候选结果精排的模型 | 与嵌入模型同源，部署一套 | Cohere 等要联网，合规不允许 |
| 生成模型 | 云端 API，经 LLM 网关路由（小模型主力 + 大模型兜底） | 写答案的模型 | 成本可控；本地无 GPU 跑不动大模型 | 单用大模型成本超预算；纯本地部署无算力 |
| 缓存 / 队列 | Redis 7 | 内存数据库，同时做缓存、限流、任务队列 | 一个组件解决三件事 | 拆成 Redis + RabbitMQ 要多维护一个 |
| 对象存储 | silo（MinIO 社区延续，S3 兼容） | 存文件的"网盘"，接口是 S3 标准 | 可自建；以后换阿里云 OSS 不用改代码 | MinIO 官方镜像已下架（`docs/adr/0010`），维护依赖社区 |
| 可观测 | Prometheus + Grafana + Loki + Langfuse | 指标、日志、LLM 调用追踪 | 都开源可自建 | 只用 print 日志 → 上线后无法定位问题 |
| 部署 | Docker Compose（单机） | 一个配置文件起所有服务 | 一条命令，不需要懂运维 | 上 K8s 会把 90% 时间花在运维上 |

**约束声明**：后续所有代码必须使用上述技术栈。
如需更换，必须先更新本文件与 AGENTS.md，并新写一份 ADR。

### 2.1 模型接入与 provider 适配矩阵

> **"支持国内外大部分模型"这句话，真正的成本不在 chat 上。**
>
> chat 类模型 90% 的厂商都提供 **OpenAI 兼容协议**，一个适配器就能覆盖；
> 真正麻烦的是另外两类：**embedding 的批量上限和维度各家不同**，
> **rerank 的返回格式差异最大、而且很多国内厂商根本没有 rerank API**。
> 所以下面按类型分别列，不要一概而论。

**适配层设计（一句话）**：在 `app/core/providers/` 下做一层薄抽象，
对外只暴露三个方法 —— `chat()` / `embed()` / `rerank()`；
所有厂商差异**只允许出现在适配器内部**，业务代码永远看到统一的入参和返回。

```
app/core/providers/
├── base.py              # 抽象基类：chat / embed / rerank 三个方法
├── openai_compat.py     # ★ 主力适配器：覆盖绝大多数厂商（含国内主流）
├── azure_openai.py      # 差异：api-version 头、部署名代替模型名
├── ollama.py            # 本地；差异：/api/embed 批量、无 rerank
├── tei.py               # 本地 embedding/rerank（HuggingFace TEI）
└── custom.py            # 兜底：手工拼请求的逃生口（必须配注释说明为什么）
```

#### （1）chat 类 —— 兼容性最好

| provider | base_url 形式 | 鉴权 | 关键差异（容易踩的） |
|---|---|---|---|
| `openai_compat` | `https://<域>/v1` | `Authorization: Bearer <key>` | 主力。覆盖国内多数厂商 |
| `azure_openai` | `https://<资源名>.openai.azure.com` | `api-key` 头（**不是 Bearer**） | 路径里要带 `api-version`；用"部署名"而非模型名 |
| `ollama` | `http://ollama:11434/v1` | 无（或任意值） | 有 `/v1` 兼容层但**流式格式略不同**；并发能力弱 |
| `vllm` | `http://vllm:8000/v1` | 无 | 本质是 OpenAI 兼容，但**并发高时容易 OOM**，要限流 |

> **三类最容易被忽略的差异**：① `max_tokens` 语义（有的含 prompt、有的不含）；
> ② 部分模型不支持 `system` 消息，必须降级为合并进首条 `user`；
> ③ 流式返回的结束标志不同（`[DONE]` 有/无）。**这三条要在适配器里统一掉，不能让业务层判断。**

#### （2）embedding 类 —— 差异在"批量"和"维度"

| provider | base_url 形式 | 关键差异 |
|---|---|---|
| `openai_compat` | `https://<域>/v1` | 有明确的**批量上限**（条数 + 总 token 双限制），超了直接 400 |
| `tei`（本地，推荐） | `http://tei:8080` | 高吞吐；批量大小受内存限制，需要压测定 |
| `ollama` | `http://ollama:11434/api` | 走 `/api/embed`（**不是** OpenAI 路径）；吞吐低 |
| 各国内厂商 | `https://<域>/v1` | 多数兼容；但**部分厂商只支持单条输入**，必须靠适配器拆分 |

> **两条铁律**：
> ① **维度必须记进 `model_configs.embedding_dim`**。bge-m3 是 1024 维，
> 换个 768 维的模型就与 `chunks.embedding` 不兼容 —— 这属于"换模型 = 全量重建向量"，
> 不是改个配置就能切的事。
> ② **是否归一化必须显式确认**。有的返回已归一化向量（余弦距离即点积），
> 有的没有。搞混了不会报错，只会让检索结果**悄悄变差**。

#### （3）rerank 类 —— 差异最大，且很多厂商没有

| provider | base_url 形式 | 关键差异 |
|---|---|---|
| `tei`（本地，本项目选用） | `http://tei:8080/rerank` | 输入是 `(query, texts[])`，返回 `index` + `score` |
| Cohere / Jina | `https://api.cohere.com/v2` | 返回字段名不同（`relevance_score`）；**联网，本项目合规不允许** |
| `openai_compat` | — | ⚠ **OpenAI 官方没有 rerank 接口**；少数第三方网关模拟了它，字段不统一 |
| 部分国内厂商 | — | ⚠ 多数**不提供** rerank API，需自建 TEI 或 Infinity |

> **结论**：rerank 这一层**不要指望"多厂商随意切换"**。
> 本项目的做法是**本地自建 bge-reranker-v2-m3（TEI）作为唯一实现**，
> 适配矩阵里其余项仅作备案。这既满足数据合规，也避免了格式适配的无底洞。

#### 4. 与本项目版本规划的关系

| 能力 | 版本 | 说明 |
|---|---|---|
| LLM 网关模块（统一出口 + 重试/超时/降级/记账） | V-1 | `AGENTS.md` R11，必须有 |
| 一套模型配置（三类各一个 + 一个备用） | V-1 / V0.1 | 可先用 `.env` 起步 |
| **配置可管理**（表 + CRUD 接口，换模型不改代码） | **V1** | 对应 `spec.md` US-09、`docs/adr/0007` |
| 多模型实例池 + 按知识库绑定不同模型组合 | V2 | 见下方"过度设计"表，**V0.1/V1 明确不做** |

## 四、在线问答链路（核心流程）

```
用户提问
   ↓
① 接入层        鉴权 · 限流 · 问题长度校验 · 注入检测
   ↓
② 权限解析      确定本次请求可见的 scope 集合（知识库/部门/密级）
   ↓
③ 缓存查询      key = 问题哈希 + **权限指纹**（R3）；命中即回放并跳过 ④—⑩
                未命中继续；Redis 不可用则降级（记 cache=error，不阻断问答）
   ↓
④ 查询改写      口语 → 检索友好（V1）
   ↓
⑤ 检索          V0.1：向量 Top-5
                V1：向量 + 全文检索各取 20 条 → RRF 融合 → 取 20
                ★ 权限条件写在 SQL 的 WHERE 里（不是取回来再筛）
   ↓
⑥ 重排          V1：Top-20 精排成 Top-5
   ↓
⑦ 上下文组装    拼装资料（带编号）+ 长度控制（不超预算）
   ↓
⑧ 生成          经 LLM 网关调用模型，强制"只依据资料 + 标注编号"
   ↓
⑨ 引用绑定      把 [1][2] 映射回真实 chunk_id
   ↓
⑩ 输出过滤      拒答判定 · PII 脱敏 · 敏感内容检查
   ↓
写回缓存（仅未命中路径）
   ↓
返回：answer + refused + citations + latency_ms + cost
```

> **③ 缓存查询为什么必须排在 ② 之后**：缓存 key 含**权限指纹**，而指纹来自
> ② 解析出的可见范围。顺序颠倒就得用"问题文本"当 key —— 那正是 R3 禁止的越权写法。
> 缓存实现见 `app/core/cache.py` + `app/services/qa.py`，运维处置见 `docs/ops-runbook.md` A13。

| 环节 | 负责什么 | 做错了用户会看到什么现象 | 关联验收标准 |
|------|---------|----------------------|------------|
| ① 接入层 | 挡掉非法输入与攻击 | 被刷接口导致费用暴涨；或注入成功泄露提示词 | AC-11、AC-15 |
| ② 权限解析 | 算出可见范围 | 看不到自己部门该看的文档 | AC-05 |
| ③ 缓存查询 | 命中则跳过 ④—⑩ 直接回放 | **不同权限命中同一份缓存 → 越权泄露**（R3，且极难复现）；或 Redis 故障被误记成"没缓存"而看不出降级 | AC-05 · R3 |
| ④ 查询改写 | 把口语变成检索友好 | 口语化提问总是搜不到东西 | AC-07 |
| ⑤ 检索 | 找出候选资料 | ① 专有名词/编号搜不到（缺关键词检索）② 明明库里有的搜不出来 | AC-07 |
| ⑥ 重排 | 把正确内容排到前面 | 正确答案在库里但排很后，被无关内容挤掉 | AC-07 |
| ⑦ 上下文组装 | 拼资料 + 控长度 | 越权内容进了上下文（权限没做对）；或超长被截断丢信息 | AC-05、AC-08 |
| ⑧ 生成 | 基于资料作答 | 答案很流畅但内容是编的 | AC-03、AC-08 |
| ⑨ 引用绑定 | 编号映射回原文 | 点开引用发现原文不支持这个结论 | AC-06、AC-08 |
| ⑩ 输出过滤 | 拒答 + 脱敏 | 该拒答却编了；或把不该外发的数字/联系方式原样输出 | AC-03、AC-09 |

### 4.1 评估链路（离线，与在线链路**解耦**）

> 在线问答是低延迟链路，评估是批处理链路。
> 两者**共用同一份检索与生成代码，但不共用进程与并发配额** ——
> 否则跑一轮评估会把线上拖慢（与 `AGENTS.md` R10 同源）。

```
┌─ 触发：make eval / 界面按钮 / CI ───────────────────────────┐
│                                                            │
│  0. 前置校验  checksum 一致？state=active？未确认题目数=0？   │
│               任一不满足 → 拒绝开始（409）                    │
│                       ↓                                    │
│  1. 冻结快照  git_commit + config_snapshot + 模型配置        │
│                       ↓                                    │
│  2. 逐条执行  每条题：检索 → 生成 → 引用回绑 → 裁判评分       │
│                       ↓                                    │
│  3. 对照检索  ★ 同一题再跑一次"只检索"（不调生成模型）        │
│                → 产出 retrieval_hit（布尔值）                │
│                       ↓                                    │
│  4. 候选归类  按规则产出 attribution_candidate（含 unclassified）│
│                       ↓                                    │
│  5. 落库      eval_runs（汇总）+ eval_run_items（逐条）      │
│                       ↓                                    │
│  6. 对比基线  config_snapshot 相同吗？不同 → comparable=false │
└────────────────────────────────────────────────────────────┘
                       ↓
       ┌───────────────┴───────────────┐
       ▼                               ▼
 人工确认归因（15—40 分钟）        导出 CSV / XLSX
 → attribution_confirmed          （浏览器打印成 PDF）
       ↓
 badcases（结论）→ promote → evals/pending/ → 人工确认 → golden_set.yaml
```

**关键约束**

| 约束 | 为什么 |
|------|-------|
| 评估与在线链路**不共用并发配额** | 一轮评估会连续调几十次模型，与在线问答抢算力会把 P95 拖垮 |
| 逐条必须存 `answer` 全文 | 不存就无法复盘，等于只留了一个无法解释的数字 |
| `retrieval_hit` 必须由**只检索**路径产出 | 这是"检索的锅还是生成的锅"唯一可信的判据（布尔值，无猜测成分） |
| 归因结论只能人工写入 | 见 `docs/adr/0008`；数据库 CHECK 约束强制"结论必须配依据" |
| `config_snapshot` 不同 → `comparable=false` | 防止把"同时改了 A 和 B"的结果当成"改 A 的功劳" |
| 评估结果**单独存**，不混进 `query_logs` | 两者口径不同（离线单条 vs 线上含缓存），混一起会让成本判断偏差一倍 |

**三层演进（不要一次做完）**

| 层 | 内容 | 版本 | 判断标准 |
|----|------|------|---------|
| **L1 地基** | `eval_datasets` / `eval_runs` / `eval_run_items` + 基线对比 | V0.1 建表，V1 接接口 | 不做就拿不到**可解释**的数字 |
| **L2 闭环** | `badcases` + 归因确认 + 线上失败回灌 | V1 | 不做，评估集永远停在纸面题目上 |
| **L3 平台** | 可视化面板、矩阵选择器、自动分类、PDF 导出 | V2 | 价值在"给人看 / 协作"，单人阶段不产生决策价值 |

---

### 4.2 SQL 数据查询通道（V2，与文档通道**共享入口、共用权限**）

> 完整设计见 `docs/text-to-sql.md`，决策与代价见 `docs/adr/0009`。
> 这里只写它**在架构里的位置**与**三条结构性约束**。

```
用户提问
   ↓
① 接入层 + ② 权限解析   ★ 与文档通道共用同一段代码（结构性约束 1）
   ↓
③ 路由（可测组件，不是一句提示词）
   规则预判(聚合词/时间词/单位词) → 分类器(小模型) → channel
   ★ confidence < 0.75 或任一环节不确定 → 回落 doc
   ↓
   ├─────────────── doc / hybrid ──────────────► 文档通道（§四）
   │
   └── sql / hybrid ──► SQL 通道
                        │
                        ④ 语义层召回  选指标 + 选表字段（受控词汇表）
                        │            config/semantic_layer.yaml（走 Git）
                        ↓
                        ⑤ 生成 SQL    经 LLM 网关（R11，Token 记账 + 降级）
                        ↓
                        ⑥ 校验        解析器校验结构 → 对象白名单 → 强制 LIMIT
                        │            ★ 不通过 → 拒答，不执行（结构性约束 2）
                        ↓
                        ⑦ 执行        只读账号 + statement_timeout + 行数上限
                        │            ★ 这是本项目唯一允许出现"非 repos 层动态 SQL"的位置
                        ↓
                        ⑧ 复述        数字只能来自结果集（R19），禁止自行计算
                        ↓
   ⑩ 输出过滤（复用文档通道 §四 的同一步）→ 统一响应：answer + citations + sql + refused + channel
```

**三条结构性约束（都不是风格问题）**

| # | 约束 | 破了会怎样 |
|---|------|-----------|
| 1 | **权限解析两条链路共用同一个函数** | 两套独立实现迟早漂移，漂移形态是"**文档里看不到、SQL 里能算出来**"——比文档越权更隐蔽，因为数字不是原文，没人会逐字比对 |
| 2 | **对象白名单校验在生成之后、执行之前** | 只在提示词里说"只许用这些表"= 把约束交给概率系统。模型大概率会听，**不听的时候没人知道** |
| 3 | **动态 SQL 执行集中在 `app/services/nl2sql/`，且必须在规则里显式声明为唯一例外** | 否则 AI 会认为它违反"只有 repos 能写 SQL"，于是要么把动态 SQL 塞进 repos（污染数据层），要么把校验省掉（安全事故） |

**保留矩阵**

| 环节 | 文档通道 | SQL 通道 | 是否共用 |
|------|---------|---------|---------|
| 鉴权 / 限流 / 长度校验 | ✅ | ✅ | **共用同一段代码** |
| 权限解析（`scope_keys`） | ✅ | ✅ | **共用同一段代码** |
| 检索 / 语义层召回 | 向量 + BM25 + RRF | 语义层指标召回 | 各自独立 |
| 生成 | 生成答案 | 生成 SQL | 各自独立，**共用 LLM 网关** |
| 事后校验 | 引用回绑 + 拒答判定 | 白名单 + 只读闸门 | 各自独立 |
| 输出过滤 / 脱敏 | ✅ | ✅ | **共用** |
| 埋点与成本记账 | `query_logs` | `query_logs` + `nl2sql_logs` | 表分开，**口径分开统计** |

> **为什么路由必须"默认回落 doc"而不是"平等竞争"**：
> 文档通道答不出来会老实说（有可靠的拒答机制）；
> SQL 通道一旦产出数字，就没人能判断它错没错。
> **不确定时，选那个会承认自己不知道的通道。** 这是本通道最重要的一条设计原则。

## 五、数据流与存储

```
原始文件（.txt / .md）
   ↓ 存原文
MinIO（对象存储）
   ↓ 解析（去页眉页脚、归一化空行）
纯文本 → 也存 MinIO（便于排查"解析对不对"）
   ↓ 分块（512 字 + 64 字重叠，按段落边界优先）
Chunk（含元数据：doc_id / 序号 / 位置 / 密级 / 可见范围）
   ↓ 向量化（bge-m3，1024 维）
向量
   ↓ 落库
PostgreSQL + pgvector（chunk 表：内容 + 向量 + ACL 字段）
```

| 存什么 | 存在哪 | 为什么这样存 | 保留多久 |
|--------|-------|------------|---------|
| 原始文件 | MinIO | 引用要能回到原文；也是唯一可信来源 | 随文档生命周期；删除时同步清 |
| 解析后文本 | MinIO | 排查"解析坏了导致答错"的唯一手段 | 同上 |
| Chunk + 向量 + ACL | PostgreSQL | **和权限元数据同库同表**，一条 SQL 完成"过滤 + 检索" | 同上 |
| 用户/知识库/文档元数据 | PostgreSQL | 业务数据 | 长期 |
| 会话 / 反馈 | PostgreSQL | 反馈用于找知识库缺口 | 2 年 |
| 审计日志 | PostgreSQL（独立表，只追加） | 合规要求；应用账号无 UPDATE/DELETE 权限 | `⚙️ 待确认，默认 3 年` |
| 任务状态 | Redis（进行中）+ PostgreSQL（历史） | 速度与可追溯兼顾 | 90 天 |
| 缓存 | Redis | key 必须含权限指纹（`AGENTS.md` R3）；**SQL 通道的 key 还须含 `semantic_layer_version`**（否则改口径后用户在拿旧数字） | TTL 1 小时 |
| **语义层（V2）** | `config/semantic_layer.yaml`（**走 Git，不进库**） | 口径改动需要逐行 diff 与人工 review；表里只存 `nl2sql_logs.semantic_layer_version` 作引用 | 随代码版本 |
| **NL2SQL 日志（V2）** | PostgreSQL（`nl2sql_logs`，一问一行） | 这是**唯一**能事后判断"它当时生成了什么 SQL、被哪道闸门拦下、用的哪个口径"的地方 | 与 `query_logs` 同周期 |

## 六、关键约束（具体数字）

| 约束 | 目标 | 超出后会怎样 |
|------|------|------------|
| 端到端延迟 P95 | < 5 秒 | 用户觉得卡，宁可去问同事 |
| 首字延迟（流式） | < 1.5 秒 | 用户以为系统卡死，重复点击 |
| 检索延迟 P95 | < 300 ms（30 万块） | 整体延迟被拖垮 |
| 单次问答成本 | < ¥0.03 | 月预算被击穿 |
| 月度总成本 | < ¥1500 | 自动降级为"仅检索不生成" |
| 并发 | 20 | 超过需要限流 + 排队 |
| 入库吞吐 | ≥ 8 块/秒（CPU） | 3000 份文档入库要跑好几天 |
| **SQL 通道总延迟（V2）** | < 6 秒 | 瓶颈在"生成 SQL"那一次模型调用，执行通常 < 100 ms |
| **SQL 通道单次成本（V2）** | < ¥0.05 | 需 2 次模型调用（生成 SQL + 复述结果），比文档通道贵；**单独记账，不与文档通道混算** |
| **SQL 执行超时（V2）** | 3000 ms | 超出抛结构化错误，**不重试**（重试会放大负载） |
| **SQL 返回行数（V2）** | ≤ 200 行 | 超出静默截断并置 `truncated=true` |

> **两个口径必须分开记**（与 `evals/README.md` 第七节同源）：
> 评估时是"离线单条成本"（无缓存命中），线上是"含缓存的平均成本"。
> SQL 通道尤其要看这个差别 —— 同一个统计问题会被重复问很多次，缓存命中率很高。

## 七、质量瓶颈与简化空间（给未来的我看的）

**1. 整个系统的质量瓶颈在哪？**

**检索质量。** 经验上端到端准确率提升的 80% 来自检索链路（分块策略、
混合检索、重排序），而不是换更强的生成模型。
**优化优先级：数据与分块 > 检索 > 提示词 > 模型。**

具体到本项目，三个最可能拖后腿的点：
- ① 解析质量（页眉页脚、表格串行会污染 chunk）
- ② 分块边界（切断句子会让语义块失效）
- ③ 权限过滤过早收窄（过滤后候选太少 → 召回不足）

**1b. V2 加了 SQL 通道之后，瓶颈排序变了。**

文档通道的瓶颈是"检索质量"（提升空间来自数据与分块）；
SQL 通道的瓶颈**不在生成，在路由与语义层**：

| 瓶颈 | 排第几 | 为什么 |
|------|-------|--------|
| **路由准确率** | 1 | 路由错会产出"语法完美、执行成功、数字真实存在、但答的不是用户问题"的答案——**静默失败**，没有任何机制能发现 |
| **语义层覆盖率与口径正确性** | 2 | 语义层没声明的对象只能拒答（可见）；口径写错则数字错（不可见，且可能长期不被发现） |
| SQL 生成正确性 | 3 | 写错会报错或返回 0 行，**可见**，且通常一轮提示词迭代能解决大部分 |
| SQL 执行性能 | 4 | 单条查询通常 < 100 ms，除非缺索引 |

> **注意这个排序与直觉相反。** 直觉是"写 SQL 最难"，实际上写错 SQL 是**廉价失败**。
> 所以工程顺序是：**语义层 → 路由 → 安全 → 评估 → 最后才是生成提示词。**
> 顺序反了，你会做出一个"演示时惊艳、上线后没人敢用"的功能。

**2. 如果时间不够，哪些部分可以先简化而不影响上线？**

- 重排序可以先不做（准确率约降 5%，延迟降 300—600ms）
- 查询改写可以先不做（口语提问召回会差一些）
- 缓存可以后加（只是慢，不会错）
- 反馈组件可以延后（但要保留表结构，后面才不用改库）
- 管理端看板整期放到 V1

**3. 有没有"过度设计"？哪些组件现在其实不需要？**

对照原需求，本项目的判断是：

| 原需求组件 | 是否需要 | 理由 |
|-----------|---------|------|
| 独立 RAG 算法微服务 | ❌ 不需要 | 算力消耗大不等于必须拆服务；单机单进程 + 并发限流即可 |
| 独立 LLM 网关服务 | ❌ 不需要（但需要"网关模块"） | 网关的**职责**必须有，但不必是独立进程 |
| 独立文档解析服务 | ❌ 不需要 | 解析在 worker 里，本身就是离线 |
| 消息队列 RabbitMQ | ❌ 不需要 | Redis 队列够用 |
| Elasticsearch | ❌ 不需要 | PG 全文检索 + pg_trgm 够用 |
| 图数据库 Neo4j | ❌ 不需要 | GraphRAG 未启用 |
| 多模型实例池 + 按知识库绑定模型 | ⚠ 拆开看 | **V0.1/V1：一套模型配置 + 一个备用即可**（`docs/adr/0007`）。但"配置可管理（换模型不改代码）"要做，见 US-09。多实例池与按库绑定放 V2 |
| K8s | ❌ 不需要 | 单人无运维能力 |
| 微前端 / 状态管理库 | ❌ 不需要 | 3 个页面用不上 |
| **Text-to-SQL 通道（V2 引入）** | ⚠ **有条件需要** | 原始需求里没有它，是后来按指示加进 V2 的。**它的前置条件不满足时应当直接推迟**（5 条见 `docs/text-to-sql.md` 第零节）。不做受控语义层而直接让模型生成 SQL，等于把数据库暴露给一个概率系统——那不是"过度设计"，是"设计缺失" |

> **这一节的价值**：半年后你回看会怀疑"是不是该上微服务了"，
> 这里写着当时的判断和理由。要改可以，但要新写一份 ADR。
>
> **关于 Text-to-SQL 的一句提醒**：它是这套文档里**唯一一个"不做也不会被用户发现，
> 做错了会静默产出错误数字"** 的功能。
> 所以对它的取舍标准不是"能不能做出来"，而是"**前置条件满足了没有**"。
> 满足就做（它能显著减少"去翻报表"的成本）；不满足就推迟，不要做半个。
