# 版本规划（releases.md）· 修正版

> **这份文件是对原需求"迭代规划"的重写。**
>
> 原规划的问题不是内容不对，而是**粒度对单人严重超标**：
> V0.1 叫"可演示 Demo"，但里面包含用户管理 + 知识库 CRUD + 文档管理 +
> 会话管理 + 问答链路 + 异步任务 + 3 个前端页面 + 指标埋点。
> 对 5 人团队是 3 周，对一个人是 2 个月——而"2 个月才有东西能演示"，
> 意味着你在第 5 周就会开始怀疑自己。
>
> 修正原则：**版本的目标不是"功能多少"，而是"风险排除多少"。**

---

## 一、版本总览（修正后）

| 版本 | 目标（一句话） | 周期 | 排除的核心风险 | 部署 | 能否给真人用 |
|------|--------------|------|--------------|------|------------|
| **V-1 骨架** | 一条命令跑通"上传 txt → 提问 → 带引用回答" | 3—5 天 | 技术栈能不能跑起来 | 本机 | 只能我自己用（命令行） |
| **V0.1 可演示** | 有页面、有权限、有评估集，能演给领导看 | 3—4 周 | 需求理解对不对、权限会不会漏 | 单机 Docker | 演示用，**禁止生产** |
| **V1 试点可用** | 试点部门真的在用，指标可监控、故障可回滚 | 6—8 周 | 质量能不能达标、出了事能不能救 | 单机 Docker | 试点部门 |
| **V2 企业增强** | 支持 PDF/Word、可视化调参、完整评估平台、**Text-to-SQL 数据查询** | 持续 | 覆盖面与可运营性 | 单机 / 视情况 K8s | 全员 |

> **为什么新增 V-1**：原规划从 V0.1 起步，但 V0.1 仍然集合了 7 个模块。
> 单人项目最需要的是**第 5 天就有一个能跑通的东西**——
> 哪怕只有命令行、没有页面、没有权限。它的价值不是能演示，
> 而是让你在投入 4 周之前，先用 5 天验证"这条路走得通"。

### 三份文件的分工（不要混淆）

| 文件 | 角色 | 内容 |
|------|------|------|
| **`docs/releases.md`（本文件）** | **四个版本范围的唯一事实来源** | 每版的 ✅做什么 / ❌不做什么 / ✓退出门禁 |
| `docs/tasks.md` | 任务清单 | 把本文件的 ✅ 拆成可单独验收的任务：V-1 → T01—T09，V0.1 → T10—T33，V1 → T40—T70，V2（摘要）→ T71—T80 |
| `.trae/rules/project_rules.md` 第 5 节 | 只放**当前版本**的摘要 | 因为它每轮对话都注入，写全四版会挤占任务上下文 |

**所以切换版本时只改两处**：本文件（新增/修订该版本的 ✅ 与 ❌）+ `project_rules.md` 第 5 节（换成当前版本）。
`tasks.md` 的任务本身不用重排，只需按新版本范围取用对应区段。

> **反例（一定要避免）**：只改 `project_rules.md` 第 5 节、忘了改本文件；
> 或者为了"完整"，把四个版本的范围全部抄进 `project_rules.md`。
> 前者会让两份文档不一致（AI 会挑一个它更喜欢的执行），后者会让常驻规则失效。

## V-1｜骨架版本（3—5 天）

**目标**：跑通一条最短的端到端链路，验证技术栈可用。

### ✅ 做什么

1. `docker compose` 拉起 PostgreSQL（含 pgvector）+ Redis
2. 一个 Python 脚本 `/scripts/ingest.py`：读一个 txt → 分块 → 调用本地 bge-m3 → 写 pgvector
3. 一个 FastAPI 接口 `POST /api/v1/query`：检索 Top-5 → 拼接提示词 → 调模型 → 返回答案 + 引用
4. **一个命令行脚本** `/scripts/ask.py` 提问（不做页面）
5. 一条 `make dev` 能起来，一条 `make test` 能跑通 3 个冒烟测试

### ❌ 明确不做

- ✗ 不做任何前端页面（**这是 V-1 最大的取舍**：前端会占掉 60% 的时间，但它不验证任何核心风险）
- ✗ 不做权限、不做用户、不做任务队列（脚本同步跑，慢就慢）
- ✗ 不做多格式解析、不做重排、不做混合检索
- ✗ 不做评估集（此时还没有系统可以评）

### ✓ 退出门禁（不满足不进 V0.1）

- [ ] 从零开始，照文档能在 30 分钟内把环境跑起来
- [ ] 上传一份真实 txt（100 页），提问相关内容，答案正确且带引用
- [ ] 提问一个知识库里没有的问题，系统明确拒答
- [ ] `make dev` / `make test` 两条命令都能用

## V0.1｜可演示版本（3—4 周）

**目标**：有页面、有权限、有评估集，能给领导做一次完整演示，并证明质量可控。

### ✅ 做什么

**1. 数据链路**
- txt / markdown 解析（含页眉页脚去除、空行归一化）
- 递归字符分块（512 字 + 64 字重叠）
- 本地 bge-m3 向量化，写入 pgvector（HNSW 索引）
- MinIO 存原文 + 解析文本

**2. 检索链路（单路，作为基线）**
- 纯稠密向量检索，Top-5
- **权限过滤下沉到 SQL**（`AGENTS.md` R2）
- 检索耗时埋点

**3. 生成链路**
- LLM 网关（超时按 provider 配置、重试 2 次、Token 记账）
- 提示词：强制"只依据资料 + 引用编号 + 固定拒答句式"（`app/prompts/answer_v1.md`）
- 引用绑定：把 `[1][2]` 映射回真实 chunk
- 拒答判定：检索分数阈值 + 模型判断双重

**4. 后端接口（严格按 `docs/openapi.yaml`）**
- 知识库 CRUD（4 个接口）
- 文档上传 / 列表 / 删除（3 个接口）
- 问答（1 个接口，非流式）
- 任务状态查询（1 个接口）

**5. 异步任务**
- Redis 队列 + 一个 worker 进程
- 仅"解析 + 向量化"一类任务；含失败重试 3 次、失败原因落库

**6. 前端（3 个页面，只做 3 个）**
- 知识库列表页
- 文档上传页（含进度与失败原因）
- 问答页（问题输入 + 答案 + 引用卡片 + 拒答态）

**7. 权限（最小可用）**
- 用数据库表定义"用户 → 知识库/部门 → 可见范围"映射
- 无管理界面，用 SQL 脚本维护
- 无登录，用 `X-KB-User` header 传测试账号
- ★ **每次问答落一行 `query_logs`（含 `scope_snapshot`）**：用户权限会变，
  这是事后排查越权问题的**唯一手段**（`data-model.md` 2.9、`security.md` 2.2）

**8. 评估（这一项不能砍）**
- `evals/golden_set.yaml` 30 条（含 refuse 6 条、permission 4 条、edge 2 条）
- `make eval` 输出三层指标
- 建立第一份基线数字
- ★ **评估结果入库**：`eval_runs` / `eval_run_items` 建表并写入
  （没有表，基线就只存在于记忆里 —— 见 `docs/adr/0008`）

### ❌ 明确不做

- ✗ RBAC 管理界面、审计日志、SSO
- ✗ PDF / Word / OCR
- ✗ BM25 混合检索、RRF、重排序（**故意不做**：作为 V1 优化的对比基线）
- ✗ 流式输出（先做完整体验，流式是体验优化不是核心风险）
- ✗ 反馈 👍👎、BadCase 挖掘
- ✗ **评估平台界面**：不做面板、不做数据集管理接口、不做导出
      （**但 `eval_runs` 表要建、结果要写** —— 这是有意的"地基早、平台晚"）
- ✗ 监控大盘、告警、K8s
- ✗ 多轮对话

> **为什么故意不做混合检索和重排**：你需要一个"改进前的数字"。
> 如果 V0.1 就把最好的都用上，V1 你就无法证明"优化有效"。
> 这是评估驱动开发的基本要求，不是偷懒。

### ✓ 退出门禁（不满足不上线试点）

- [ ] `docs/spec.md` 中所有 `[V0.1]` 标记的验收标准全部通过
- [ ] 评估集 ≥ 30 条，四类齐全，**标准答案全部经我人工确认**
- [ ] 各项指标：Recall@5 ≥ 0.85、MRR ≥ 0.70、忠实度 ≥ 0.85、
      拒答正确率 ≥ 0.90、误拒率 ≤ 0.05
- [ ] P95 延迟 < 5s，单次成本 < ¥0.03
- [ ] 越权测试全部通过（含缓存不串权限）
- [ ] 至少一次**真实的评分演练**：故意问一个知识库里没有的问题，确认拒答
- [ ] 演示脚本走通：上传 → 提问 → 点引用看原文 → 提问无答案看拒答
- [ ] 评估结果已入 `eval_runs`，且**能回答"这条数字是哪个 commit 跑的"**（SQL 查得到）

## V1｜试点可用版本（6—8 周）

**目标**：一个部门真的在用，指标可见，故障可回滚。

### ✅ 做什么

**1. 检索质量升级（本项目最高杠杆）**
- 混合检索：向量 + PostgreSQL 全文检索（不装 ES）
- RRF 融合
- bge-reranker-v2-m3 重排（Top-20 → Top-5）
- 查询改写（规则 + 小模型：口语 → 检索友好）

**2. 权限与合规**
- 完整 RBAC（4 种角色）
- **审计日志**：只追加、不可修改、含 who/when/what/target/result
- **文档删除全链路清理**（原文 + 文本 + chunk + 向量 + 缓存 + 评估集引用）见 AC-19
- 登录 + JWT

**3. 稳定性与运维**
- WebSocket / SSE 流式输出（含降级：WS 不可用回退到轮询）
- 模型故障降级 + **全局降级开关**（一键盘关闭 LLM，只返回检索结果）
- 成本预算硬上限 + 超限自动降级
- Prometheus 指标 + Grafana 大盘 + 3 条关键告警
- 一键回滚脚本（目标 < 5 分钟，**必须真实演练过**）

**4. 反馈与迭代闭环（★ 本轮补齐：从"能跑"升级为"能积累"）**
- 👍👎 反馈 + 原因选择 → 落 `feedback` 表（**候选**，含误报）
- **人工确认后进入 `badcases` 表（结论）**，含归因、判定依据、定级
- "答不出来的问题排行"页面
- **评估地基**：数据集元数据接口 + 异步评估任务 + 逐条结果 + `changed_only` 回归对比
- **归因闭环**：`make eval-attribute` 只跑检索、产出 `retrieval_hit` 与归因**候选** →
  我逐条确认结论（**必须留判定依据**）→ 未确认的不计入任何统计
- **线上失败回灌**：badcase → promote 成**候选题目**（进 `evals/pending/`）
  → 我确认标准答案后合入 `golden_set.yaml`
- 评估集扩到 100+ 条，含线上失败案例
- 报告导出 **CSV / XLSX**

**5. 存储升级**
- 向量库仍为 pgvector（不做迁移，见 `docs/adr/0002`）
- 引入备份策略：数据库每日备份 + MinIO 快照

**6. 生成与拒答质量（V0.1 评估实证驱动）**
- **引用绑定校验修复**：R6 数字校验只查被引块，模型引错块时稳定误拒
  （Q008/Q030，run 68/87/97 三次复现）→ V1 扩展校验范围至全部检索块，或自动重绑
- **时间语义代码级解析**：问题时间词与检索块时间错配时该拒未拒（Q027 两次复现）
  → V1 在生成前加代码级时间比对（不靠提示词）
- **澄清式拒答**：拒答从"仅固定句式"升级为"固定前缀 + 一句澄清提示"
  （Q029 裁决，V0.1 金标已收敛为纯句式，数据集 v1.0.3）

### ❌ 明确不做

- ✗ PDF / Word / Excel / OCR
- ✗ 可视化策略配置（策略写配置文件，不做界面）
- ✗ GraphRAG / Self-RAG / Agentic RAG
- ✗ **评估可视化面板、「知识库 × 策略 × 模型」任务选择器、自动归因分类器**
      V1 的评估能力是"结果入库 + 逐条对比 + 候选归类 + 人工确认 + Excel 导出"。
      面板与矩阵选择器属于"给人看 / 协作"那一层；自动分类器须先验证准确率。
      完整理由与复核条件见 `docs/adr/0008`
- ✗ 服务端 PDF 导出（改用浏览器"打印成 PDF"，零后端成本）
- ✗ K8s、微服务拆分
- ✗ SSO、行级权限

### ✓ 退出门禁

- [ ] 评估集 ≥ 100 条，四类比例达标（normal 60% / refuse 20% / permission 10% / edge 10%）
- [ ] 检索指标相对 V0.1 基线**有可量化的提升**，且忠实度不下降
- [ ] 数据集含未确认题目时发起评估 → 被拒（409），且提示"还有 N 条未确认"
- [ ] 改动了 `golden_set.yaml` 但未重新注册 → 发起评估返回 409 `STALE_DATASET`
- [ ] 连续两次评估能自动列出"**哪几条从 pass 变 fail**"
- [ ] 报告里"未确认归因 N 条"与逐条数据一致，未确认的行不出现在任何汇总里
- [ ] 至少 10 条题目来自线上真实失败案例，且走的是 promote → 人工确认通道
      （`golden_set.yaml` 的每次改动都能在 git log 里看到是人提交的）
- [ ] 流式首字延迟 < 1.5s
- [ ] 压测：20 并发下 P95 延迟上升不超过 2 倍，无 500
- [ ] 审计日志不可修改（已验证）
- [ ] 删除一份文档后，全库搜索其任意片段为 0 结果
- [ ] **回滚演练成功**：从触发告警到恢复服务 < 5 分钟
- [ ] 试点部门连续使用 1 周，无 P0 故障

## V2｜企业增强版本（持续）

**做什么**（按性价比排序，不是并列）

1. **PDF / Word / Excel / HTML 解析 + OCR**（覆盖剩余 55% 文档，这是覆盖率的最大瓶颈）
2. 可视化策略配置平台（分块 / 检索 / 重排 / 查询改写参数，带预览）
3. **评估平台化**：可视化指标面板与图表、
   **「知识库 × 策略 × 模型」矩阵选择器**、
   自动归因分类（**上线前须先用人工标注 50 条验证准确率，低于 85% 就不做**）、
   报告 PDF 导出（浏览器"打印成 PDF"，**不做服务端渲染**，见 `docs/adr/0008`）

   > **注意：评估的"地基与闭环"在 V1 就已完成** —— 结果入库、逐条回归对比、
   > 候选归类、人工确认、线上失败回灌、Excel 导出。
   > V2 加的是"给人看"的那一层，不是"能不能拿到正确数字"那一层。
   > 何时该做，见 `docs/adr/0008` 第六节复核条件 2。
4. SSO + 细粒度行级权限
5. GraphRAG 试点（**仅离线构建，默认关闭**）
6. ★ **Text-to-SQL 数据查询通道**（`docs/text-to-sql.md`、`docs/adr/0009`）

   > **这一项带前置条件，不是"排到就做"。** 见下方「V2-6 的前置条件」。
   > 它最大的风险不是"SQL 写错"，而是**路由错**——
   > 生成一条语法完美、能跑通、返回一个数、但答的不是用户问题的 SQL。
   > 这种错误**没有任何机制能让人发现**（没有引用可点、没有原文可对），
   > 与文档通道"答错时引用对不上"的可见失败完全不同。

   **这一项做什么**

   - 语义层（`config/semantic_layer.yaml`，走 Git）：受控的表/列/指标口径
   - 显式三阶段路由（规则预判 → 分类器 → 失败回落），**不确定时默认回落文档通道**
   - SQL 安全五道闸门：只读账号 → 语句解析校验 → 对象白名单 → 强制 LIMIT → 超时配额
   - 权限与文档通道**同源**（复用同一段权限解析，拼进 SQL 的 WHERE）
   - 结果必须展示 SQL；每个指标声明 `scope_mode` 并在答案里标注聚合范围
   - 独立评估：执行准确率（比结果集）+ 路由准确率 + 拒答正确率，跑在固定种子数据集上

   **V2-6 的前置条件（任一不满足 → 推迟，不要"先做出来再说"）**

   | # | 前置条件 | 怎么验证 |
   |---|---------|---------|
   | 1 | 有结构化数据源，且有**只读**账号 | 用只读账号跑通一条 `SELECT` |
   | 2 | 有 **≥ 20 条真实统计类提问** | 落成 `evals/sql/golden_set_sql.yaml` |
   | 3 | 核心指标的**业务口径说得清**（时间字段 / 含税 / 状态过滤 / 跨期规则） | 语义层能覆盖评估集 90% |
   | 4 | V1 门禁全绿（拒答边界与评估体系已稳定） | V1 退出门禁全部勾选 |
   | 5 | 数据源的**权限模型已知**（谁能看哪些行），且能映射本项目的 `scope_key` | 能回答"销售用户该不该看到全公司平均" |

**明确不做 / 延后**

- ✗ 大规模 GraphRAG 增量更新优化
- ✗ 多模态 RAG 生产级调优
- ✗ K8s（除非同时在线 > 100 人，否则不划算）
- ✗ SQL 通道的**多工具 Agent 自动编排**（混合问题只并列展示，不融合）
- ✗ SQL 通道的**自动 schema 发现**（schema linking 前置到语义层）
- ✗ SQL 通道的**语义层可视化编辑界面**（语义层走 Git，改动需要 diff 与 review）
- ✗ SQL 通道的**跨库联邦查询**（一个通道只连一个数据源）
- ✗ SQL 通道的**明细行级数据导出**（只返回聚合结果；明细走原报表系统）

> **关于 GraphRAG 的成本提示**：它的建图 Token 消耗通常是普通入库的 10—100 倍。
> 在开启之前必须先算一笔账：现有 3200 份文档建一次图要花多少钱、多长时间。
> 单机无 GPU 环境下，很可能"建一次图比一年问答还贵"。**先算账，再试点。**

### ✓ V2 退出门禁（按"做了哪一项就勾哪一项"）

- [ ] PDF/Word/Excel/OCR：解析成功率 ≥ 95%，且新增格式不降低原有格式的成功率

## 二、与原规划的差异对照

| 项 | 原规划 | 修正后 | 修正理由 |
|----|-------|-------|---------|
| 起步版本 | V0.1 含 7 个模块 | 新增 **V-1 骨架**（无前端、无权限） | 单人需要"第 5 天就能跑"，而不是"第 2 个月" |
| 前端 | V0.1 就有 3 个页面 | V-1 无前端；V0.1 保留 3 页 | 前端不验证核心风险，但确实要演示 |
| 检索 | V0.1 直接上混合检索 + RRF | V0.1 纯向量，V1 再上混合 | 需要"改进前的基线数字"，否则无法证明优化有效 |
| 微服务 | V0.1 就拆 RAG 算法服务 | 全程**单体模块化**（`docs/adr/0001`） | 单人维护 7 个服务 = 把时间全花在运维上 |
| 向量库 | V0.1 Chroma → V1 换 PGVector/Milvus | 从 V-1 就用 pgvector | 避免一次不必要的迁移（数据 + ACL 都要迁） |
| 消息队列 | V0.1 RabbitMQ / RedisMQ | 全程 Redis | 少一个中间件 |
| 评估 | V2 才有"完整评估平台" | **V0.1 就有 30 条评估集 + 命令行 + 结果入库；V1 补数据集/运行接口与回灌闭环；面板与选择器留 V2** | 没有评估集，前 3 周的优化方向几乎一定是错的（指南 5.8 血泪教训）。拆成"地基 → 闭环 → 平台"三层，地基和闭环不能跟着平台一起推到 V2 |
| 根因分析 | V2 做"自动识别 BadCase + 根因推荐" | V1 做**候选归类 + 人工确认 + 对照实验法**；自动分类器留 V2 且须先验证准确率 | 三类失败在自动指标上耦合，自动分类准确率不足；对照实验的判定依据是布尔值，准确率接近 100%（`docs/adr/0008`） |
| 权限 | V0.1 无 → V1 完整 RBAC | V-1 无 → V0.1 最小可用（表 + SQL 维护）→ V1 完整 | 权限是横切关注点，事后补测遗漏率极高（实测过 6 处越权） |
| 部署 | V1 Docker Compose → V2 K8s | 全程 Docker Compose，V2 视情况 | 单人上 K8s 后 90% 时间会花在运维 |
| 数据查询 | 原需求没有（Text-to-SQL 是案例里带进来的） | **V2 引入，但带 5 条前置条件**；语义层前置 + 默认回落文档通道 + 五道闸门 | 这是唯一会产出"看起来完全正确的错误数字"的功能；不做受控词汇表就等于让概率系统直接面对数据库（`docs/adr/0009`） |
| 混合问题 | — | **只并列展示，不自动融合**；不做 Agent | 融合需要模型在两组异质信息间推理，而推理错误的形态又是静默的；固定四步流水线每一步都能单独测，Agent 的自由编排只能整体测 |
