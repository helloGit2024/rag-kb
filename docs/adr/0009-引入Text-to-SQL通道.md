# ADR-0009：引入 Text-to-SQL 通道（语义层前置 + 默认回落文档）

- 状态：已采纳（**带前置条件**：见第零节，任一不满足则应推迟）
- 日期：2026-10-13
- 决策人：（你的名字）

---

## 一、背景

V2 要在问答入口后面增加一条"自然语言 → SQL → 只读执行"的数据查询通道，
用来回答**统计类问题**（上个月培训支出多少、各部门差旅排名、报销单量趋势）。
文档通道只能答"制度怎么规定"，答不了"实际是多少"。

已具备的条件：V1 的门禁全绿（拒答边界稳定、评估体系可用）、
生成与检索链路稳定、权限用 `scope_key` 下沉到 SQL 的做法已验证。

约束：**单人开发，每天 1.5 小时，我不懂前后端但懂 RAG 与业务口径，
预算极低（单次问答 < ¥0.03），无专职运维。**

一个必须写下来的前提：**这个通道的风险形态与文档通道完全不同。**

| | 文档通道 | SQL 通道 |
|---|---|---|
| 答错的样子 | 引用对不上原文 → 用户点开就发现 | **数字流畅、格式正确、没有任何异常** |
| 谁来发现错误 | 用户（看一眼引用就知道） | **没人**（除非拿去和业务系统对账） |
| 最重要的风险 | 检索质量 | **路由错**（比"SQL 写错"严重得多） |

---

## 二、备选方案

| 方案 | 一句话说明 | 好处 | 代价 |
|------|-----------|------|------|
| A. **不做** | 统计类问题继续靠人工查报表 | 零风险、零成本 | 用户拿不到即时数据；但这个需求可以通过"接一个 BI 工具"满足，不必自研 |
| B. **让模型直接看整库 DDL 自由生成 SQL** | 把数据库结构全塞进提示词，模型自己挑表写 SQL | 实现最快，演示效果好 | 表一多必错；提示词爆炸；**口径全靠模型猜**；无法保证只读与权限；等于把数据库暴露给一个概率系统 |
| C. **Agent 自主体**（多工具自由编排） | 让 Agent 自主决定查文档还是查库、可多步推理融合 | 能力最强，混合问题体验好 | 流程不可预测、评测困难；`docs/adr/0005` 已明确不引入编排框架；单人无法维护一个不可预测的链路 |
| D. **★ 语义层前置 + 显式路由 + 五道闸门 + 单次流水线** | 受控词汇表 + 可测路由 + 结构性安全 + 固定四步 | 每个失败都可解释、可测、可归因；不引入编排框架 | 需要**人工维护语义层**（含业务口径）；混合问题只能并列展示，不能融合；覆盖率低于 B/C |
| E. 只做"明细查询"，不做聚合 | 只支持"某张单子的状态"这类查询 | 绕开聚合与行级权限的冲突 | 用户真正想要的就是聚合（"多少钱""排名"），做了等于没做 |

---

## 三、决策

选定：**D**，并接受两条边界：

1. **V2 只做单表/两表 JOIN 的聚合与明细**，混合问题（同时问制度与数字）**只并列展示、不自动融合**；
2. **跨范围聚合不静默执行** —— 每个指标必须声明 `scope_mode: own | global`，
   `own` 的答案文案必须标注"基于你有权访问的 N 条记录"。

具体形态：

- **语义层**（`config/semantic_layer.yaml`，走 Git）是唯一允许的表/字段/口径来源；
  模型只能在声明过的对象里选，引用未声明对象一律**拒答（不猜近似字段）**；
- **路由**做成显式三阶段组件（规则预判 → 分类器 → 失败回落），
  **不确定时默认回落文档通道**（因为文档通道有可靠的拒答机制）；
- **SQL 安全五道闸门**：只读账号 → 语句结构校验 → 对象白名单 → 强制 LIMIT → 超时配额，
  任何一道不通过**不执行**；
- **结果必须展示 SQL**（可折叠）—— 可审计 + 让用户能发现口径错；
- **评估独立**：执行准确率（比结果集，不比 SQL 文本）+ 路由准确率 + 拒答正确率，
  在**固定种子数据集**上跑。

---

## 四、理由

1. **风险排序决定了工程顺序：路由 > 口径 > 生成 > 执行。**
   直觉上"写 SQL 难"，实际上 SQL 写错会报错或返回 0 行（可见失败），
   而路由错会给出一个**语法完美、执行成功、数字真实存在、但回答的不是用户问的问题**的答案。
   所以先做可测路由，再做生成提示词。

2. **语义层的真正价值是"把业务口径从人的脑子里搬到 Git 里"，不是"给模型一张表结构"。**
   同一句"上个月培训支出"，因为（时间字段 × 是否含税 × 单据状态 × 跨期规则）
   可以有 4 个都"正确执行"的答案。这段差异是业务知识，模型猜不出来 ——
   而它一旦猜错，错误是不可见的（数字看起来完全合理）。**这是本通道唯一的不可自动化部分。**

3. **权限必须同源，否则会产生"更隐蔽的越权"。**
   文档越权会暴露原文，有人会去比对；SQL 越权只暴露一个数字，
   没人会想到去核对聚合范围。所以两条链路复用同一段权限解析代码。

4. **"默认回落 doc"是一条低成本、高收益的设计。**
   文档通道答不出来会老实说；SQL 通道一旦产出数字就没人能判断。
   **不确定时，选那个会承认自己不知道的通道。**

5. **安全必须靠数据库权限，不能靠提示词。**
   提示词层面挡注入是概率性的（模型可能不听），
   只读账号是确定性的（听了也执行不了）。**SQL 通道的注入防护 90% 由那一个 `GRANT SELECT` 承担。**

6. **不引入 Agent，是因为"评测不了的东西就不能上生产"。**
   固定四步流水线的每一步都能单独测（路由可测、生成可测、校验可测、执行可测）；
   Agent 的自由编排只能整体测，出错无法归因到具体步骤。

## 五、代价（必填，不允许留空）

1. **必须人工维护语义层，且它需要持续更新。** 新表、新字段、口径变动都要改文件。
   **这是长期成本，不会消失。** 缓解：语义层只覆盖"被问到的对象"，不做全库映射；
   未声明的对象拒答即可 —— 拒答是安全的，猜是危险的。

2. **混合问题体验差。** "报销标准和上月平均报销额分别是多少"只能并列两块结果，
   用户需要自己看。这是**有意为之**：融合需要模型在两组异质信息间做推理，
   而推理错误的形态又回到"静默"。

3. **覆盖率会明显低于"自由生成 SQL"方案。** 语义层没声明的表就查不了，
   用户会觉得"明明数据库里有这个字段"。缓解：把拒答原因做成可运营指标
   （`reject_reason=unknown_object` 的排行），按排行**按需**补语义层。

4. **多一次模型调用，成本与延迟都上升。** 单次问答成本从 < ¥0.03 升到 < ¥0.05；
   延迟瓶颈在"生成 SQL"这一步。评估与线上必须**分开记口径**。

5. **聚合与行级权限的冲突只能缓解，不能消除。** 方案是"逐指标声明 `scope_mode` + 答案标注范围"，
   但它依赖**我（业务侧）把 `global` 白名单定对**。定漏了会拒答（可见），
   定多了会越权（不可见）—— 所以白名单必须**从空开始、按需增加**。

6. **评估需要维护固定的种子数据集。** 每次评估要建临时库、灌 `seed.sql`、跑完销毁。
   比文档通道的评估重。但这是唯一能测"口径错"的手段 ——
   生产数据里"跨年报销单""已驳回单据"这类边界数据太少，测不出来。

7. **排查链变长。** 从"答案不对"到"问题在哪"要经过：路由 → 语义层召回 →
   生成 → 校验 → 执行 → 复述。所以 `nl2sql_logs` 必须记录每一步的中间产物
   （生成的 SQL、校验结果、被拒原因、结果摘要），否则排查无从下手。

8. **需要新增一个依赖（SQL 解析库，如 `sqlglot`）。** 违反 R12 的默认立场
   （"能不加就不加"）。理由是白名单校验必须解析 SQL 对象引用，
   用正则做这件事**一定会被绕过**（注释、大小写、别名、quote 都能骗过正则）。代价：多一个依赖要维护。

## 六、复核条件

满足**任意一条**即重新评估本决策：

1. **语义层覆盖不了评估集的 90%** → 说明"受控词汇表"这个前提不成立，
   要么补语义层，要么退回方案 E（只做明细）。**这时不是该放开自由生成，是该重新审视数据源。**
2. **路由准确率长期低于 0.85** → 说明"两个通道可以用一次分类器分开"这个假设错了。
   考虑：把 SQL 通道做成**显式入口**（用户自己选"查数据"），
   **放弃自动路由** —— 把不确定的自动化换成确定的交互。
3. **出现一次"静默跨范围聚合"导致的错误结论**（`scope_mode=own` 但答案未标注范围、
   或 `global` 白名单定多了）→ 立即收紧为"所有聚合默认 own"，并补一条硬门禁。
   **这是本决策里唯一不可接受的失败形态。**
4. **需要支持 > 2 张表 JOIN 或子查询** → 说明真实需求已经超出"受控查询"，
   应引入更强的结构（如查询模板/参数化模板），而不是放开生成自由度。
5. **混合问题占比超过 30%** → 应重新考虑多工具编排（届时需先解决"可评测"问题：
   必须能为每一步单独写测试）。**在那之前不做 Agent。**
6. **数据源本身变化**（换成另一个库/加了新库/权限模型变了）→
   语义层与权限映射都要重做，必须重走本 ADR。

## 七、作为不懂技术的人，我只需要确认哪一点？

**你只需要确认三件事，都不需要写代码：**

1. **口径** —— 每个核心指标按哪个时间字段、含不含税、算不算未审批的单据。
   这套口径由你（或对应的业务同事）定，AI 替不了。
2. **`scope_mode` 白名单** —— 哪些指标可以给"全公司口径"，其余一律只在本人权限范围内算。
   **建议从"只有公司总人数允许 global"开始，按需增加。**
3. **接受"覆盖率低但可靠"** —— 语义层没声明的对象会拒答，用户会觉得"数据库里明明有"。
   你接受这个体验，换来的是"**没有一个数字是错的**"。

如果这三条里任何一条你答不上来，就把这个通道推到 V3 —— 前置条件不满足时，
做出来的是一个"演示时惊艳、上线后没人敢用"的功能。
