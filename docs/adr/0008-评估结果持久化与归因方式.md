# ADR-0008：评估结果入库，归因采用「候选归类 + 人工确认」

- 状态：已采纳
- 日期：2026-10-12
- 决策人：（你的名字）

---

## 一、背景

评估是这个项目里**唯一**能回答"这次改动是进步还是退步"的手段
（见 `evals/README.md` 开头）。但原设计里它存在三个具体问题：

1. **结果只落文件**：`evals/report/YYYY-MM-DD.json` 一堆散文件 +
   `docs/quality-gates.md` 里手工填的回归表。
   跑到第 4、5 次评估时，"这次是跟哪个基线比"这个问题的答案**只存在于我的记忆里**。
2. **无法回答"哪几条变差了"**：只有汇总指标，不知道是 3 条题崩了还是 30 条均匀掉一点。
   而这两种情况的修法完全不同。
3. **原需求要求"自动识别 BadCase 并给出优化方向"**，
   但我知道三类失败（召回失败 / 幻觉 / 答非所问）在自动指标上是耦合的，
   直接按自动分类器实现会得到一个不可信的分组。

约束：单人开发，每天 1.5 小时，评估集 30 条起步 → 100 条，
预算极低（单次问答 < ¥0.03），我不懂前端。

---

## 二、备选方案

| 方案 | 一句话说明 | 好处 | 代价 |
|------|-----------|------|------|
| A. 维持现状 | 结果落 JSON 文件，归因全靠人工看 | 零成本，改动最小 | 基线不可审计；回归对比靠手工维护的表格，超过 3 次评估必然失控 |
| B. 结果入库 + LLM 自动分类归因 | 跑评估时让模型直接判定每条属于哪类失败 | 看起来"智能"，全自动 | 分类准确率不足（三类失败在指标上耦合）；错误分组会把我引向修一个没坏的地方 |
| C. **结果入库 + 规则产候选 + 人工确认结论** | 规则只产出"疑似"，结论必须我点确认 | 判定依据是布尔值，准确率接近 100%；成本几乎为零 | 每轮评估多约 15—30 分钟人工确认；无法做到"全自动出优化建议" |
| D. 现在就做完整评估平台 | 面板 + 任务选择器 + 自动分类 + PDF 导出 | 好用、可协作 | 平台化的价值在"多人协作看报告"，单人项目里 80% 的决策价值由 CLI + 一份报告覆盖；会重演"两个月才有东西能演示"的错误 |

---

## 三、决策

选定：**C**。

具体形态：
- 评估结果入 `eval_runs`（含 `git_commit` + `config_snapshot`）与 `eval_run_items`（逐条）；
- 题目本体**不进表**，仍是文件（MinIO 归档 + Git 版本控制），表里只存元数据与 checksum；
- 归因分两栏：`attribution_candidate`（规则产出的候选）与 `attribution_confirmed`（人工确认的结论）；
  **只有后者非空才计入统计**；
- 归因方法用**对照实验法**（同一题分别只跑检索 / 跑完整链路），
  判定依据是 `retrieval_hit` 这个**布尔值**，不是模型打的分；
- BadCase 与 feedback **分成两张表**：feedback 是候选，badcases 是结论。

---

## 四、理由

1. **"候选"与"结论"分离，是这个决策的核心。**
   它同时解决了三件事：自动化的边界（机器只做它能确定的事）、
   归因的可审计性（每条结论都有依据和确认人）、
   以及我自己不用在"信不信 AI 的判断"上纠结——因为它压根不做判断。

2. **对照实验法的准确率是 100%，成本是几厘钱。**
   自动分类器做不到 100%，而它省下的那 15 分钟，
   代价是我可能花两天去修一个没坏的地方。这个交换不成立。

3. **`git_commit` + `config_snapshot` 是"可对比"的前提。**
   没有它，两次评估的数字不可比，而"不可比的数字"比"没有数字"更危险——
   前者会让你得出错误结论并深信不疑。

4. **题目存文件、结果入库，形态不同是因为用途不同。**
   题目要逐行 diff、要人工逐字 review 标准答案 → 文件形态最好；
   结果量大、要跨 run 关联查询 → 必须进表。

5. **平台化（方案 D）诚实地说，一部分是"想要"而不是"需要"。**
   在 100 条题、单人使用的前提下，`make eval` + 一份 Excel 报告
   能覆盖全部决策场景。面板留到 V2，那时才有真实的报告阅读需求。

---

## 五、代价（必填，不允许留空）

1. **多两张表 + 一套接口**（4 张表、14 个接口），
   比"跑个脚本打印表格"重得多。我必须在 V0.1 就把表建起来，
   不能等"以后需要再说"——因为评估本身是 V0.1 的退出门禁。
2. **归因永远有人工环节。** 我要接受"系统不会自动告诉我原因"。
   如果哪天我发现自己期待一个"自动归因机器人"，说明我在逃避那 15 分钟的确认工作。
3. **候选规则调错会产生误导性分组。** 缓解措施：允许 `unclassified` 大量存在
   （诚实的"未归类"比编造的结论有价值），并规定"同一类错判出现 3 次就改规则"。
4. **`eval_run_items` 存 `answer` 全文**，数据量随评估次数线性增长
   （100 条 × 50 次 = 5000 行）。当前规模完全无压力，
   但要知道它**不属于可以随手清空的数据**——清了就无法复盘历史失败。
5. **表元数据与数据集文件需要手工同步。** 忘记同步就会出现
   "表里说跑的是 A 版、实际跑的是 B 版"。缓解措施：跑评估前校验 checksum，
   不一致就拒绝开始（H21）。
6. **没有可视化面板。** 看指标要靠 `make eval-report` 的输出或导出的 Excel。
   在单人阶段这不是问题；但如果将来要向别人汇报，会需要它。

---

## 六、复核条件

满足**任意一条**即重新评估本决策：

1. 评估集超过 1000 条，或需要**多人同时维护**数据集
   → 把题目本体也入库（那时文件形态的 diff 优势被协作成本盖过）。
2. 需要做 **> 5 个配置组合的矩阵对比**（如 3 种分块 × 3 种检索）
   → 需要任务选择器与批量运行（V2 范围）。
3. **候选归因的人工确认工作量超过每轮 2 小时**
   → 这说明候选规则该重做，**不是**该加自动分类器。
   先检查是不是 `unclassified` 比例过高导致我要从零判每一条。
4. 出现一次因"表与文件不一致"导致的**错误结论**
   → 把 checksum 校验从"跑评估前提醒"升级为硬门禁（当前是 H21）。
5. 有外部要求以 **PDF** 交付评估报告
   → 优先用浏览器"打印成 PDF"（零后端成本），只有在需要批量/自动化生成时才做服务端渲染。

---

## 七、作为不懂技术的人，我只需要确认哪一点？

**你只需要确认：归因结论永远需要你点一下确认，系统不会自动告诉你原因。
你接受这个 15—30 分钟的固定工作量，换来的是"结论一定是对的"。**
