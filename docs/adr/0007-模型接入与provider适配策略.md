# ADR-0007：模型接入以「OpenAI 兼容为主 + 本地自建兜底」，模型配置做成可管理的表

- 状态：已采纳
- 日期：2026-10-23
- 决策人：我

---

## 一、背景

原需求第 4 节写了"模型配置管理模块"，包含：模型信息 CRUD（Chat / Embedding / Rerank / OCR）、
连通性测试、模型池管理（多实例、按知识库绑定）、Token 成本记账。
而我在实例文档里**一度只落地了"LLM 网关"这个运行时出口，漏掉了配置管理这一整个面** ——
`spec.md` 的 US-09（"换模型不用改代码"）因此悬空：AI 会把模型配置写死进 `.env` 或代码常量。

同时，"支持国内外大部分模型"这句话需要拆解。它的真实成本分布很不均匀：

- **chat**：90% 的厂商提供 OpenAI 兼容协议，成本很低
- **embedding**：批量上限、向量维度、是否归一化，各家都不同
- **rerank**：格式差异最大，且**很多国内厂商根本不提供 rerank API**

约束（来自 `docs/constraints.md`）：
- 单人维护，出了问题只能自己查
- 数据不出内网 → 嵌入/重排必须本地部署；可调用云端 chat API，但只允许传检索片段
- 月度预算 ≤ ¥1500（`⚙️ 待你确认`），不允许"先用最强模型再说"
- 无 GPU → 本地 embedding 走 CPU，吞吐是硬瓶颈
- V0.1—V1 不启用高阶 RAG，也不做多知识库绑定不同模型

---

## 二、备选方案

| 方案 | 说明 | 好处 | 代价 |
|------|------|------|------|
| A. 通用网关框架（LiteLLM / One-API 等） | 现成的多厂商代理层 | 覆盖厂商多；自带 key 管理、限流、成本统计 | 又是**一个黑盒 + 一个要运维的服务**；与 ADR-0005 冲突；出错时我分不清是我的 bug 还是网关的 |
| B. 每个厂商写一个完整适配器 | 全自研，逐家实现 | 完全可控 | 厂商数量是 N，工作量是 O(N)，且大部分是重复劳动（都是同一套 OpenAI 协议） |
| C. **OpenAI 兼容为主 + 少量例外自建** | 一个主力适配器覆盖 90%，只为例外写薄适配 | 工作量 O(1) 而非 O(N)；差异集中在一层 | 少数厂商的特有能力（如特定 rerank 格式）需要自己补；兼容层可能掩盖厂商的真实差异 |

关于"模型配置放哪儿"，另有三个子方案：

| 子方案 | 好处 | 代价 |
|---|---|---|
| C1. 全部写死在 `.env` | 最简单，零代码 | **US-09 无法满足**：换模型要改代码 + 重新发布；也没人能回答"线上现在跑的是哪个模型" |
| C2. 全部放配置文件（`models.yaml`），提交进仓库 | 版本可追溯；改动要过 review | 改配置仍需重启；API Key 会进版本库（违反 R1） |
| C3. **配置存数据库表 `model_configs`，Key 只存引用** | 改配置不动代码、不重启；Key 不落库 | 多一张表 + 一套 CRUD 接口 + 权限控制；键名写错时要靠 `model-test` 才能发现 |

---

## 三、决策

选定：**方案 C + C3**

1. **接入层**：`app/core/providers/` 下做一层薄抽象，对外只暴露 `chat()` / `embed()` / `rerank()` 三个方法。
   主力适配器 `openai_compat.py` 覆盖绝大多数厂商；只为例外（Azure、Ollama、本地 TEI）各写一个薄适配器。
   **所有厂商差异只允许出现在适配器内部**，业务代码永远看到统一入参和返回。
2. **配置存储**：模型配置存进数据库表 `model_configs`（见 `docs/data-model.md` 2.10），
   通过 `GET/POST/PATCH/DELETE /api/v1/admin/models` 管理，**不需要改代码、不需要重启**。
3. **密钥**：`model_configs.api_key_ref` 只存**环境变量名或密钥服务路径**，
   绝不存明文（`AGENTS.md` R1）。`model-test` 接口收到的 `api_key` 是一次性输入，测试完即丢。
4. **rerank 层不做多厂商**：本地自建 bge-reranker-v2-m3（TEI）作为唯一实现，
   适配矩阵里其余项仅作备案。

## 四、理由

1. **"支持国内外大部分模型"本质上是一道协议题，不是一道厂商题。**
   OpenAI 的接口事实上已是行业通用协议，国内主流厂商（DeepSeek、通义、智谱、月之暗面等）
   基本都提供 `/v1/chat/completions` 兼容端点。写 1 个适配器还是写 12 个，
   对"能接哪些厂商"的结果几乎没影响，但工作量差一个量级。

2. **真正的差异集中在 embedding 和 rerank，所以只在这两处做投入。**
   - embedding 的差异是**批量上限、维度、是否归一化** —— 这三项靠 `model_configs` 的
     三个字段（`batch_limit` / `embedding_dim` / `params`）表达，不需要代码分支。
   - rerank 的差异是**格式**，而且很多厂商压根没有这个 API。
     与其为不存在的接口写适配，不如**本地自建一个**：既满足数据合规，又只有一个实现。

3. **配置必须可改，否则 US-09 就是一句空话。**
   我自己就是那个要频繁对比模型的人（换嵌入模型、换 chat 模型做评估对比）。
   如果每次都要改代码 → 提交 → 重新部署，我会因为麻烦**放弃做模型对比实验**，
   而模型对比恰好是 V1 优化路径里的一环。

4. **但"多模型实例池 + 按知识库绑定模型"不做。**
   那是给"多租户、每个部门用不同模型"的场景准备的。本项目 200 个用户、一个知识库体系，
   这个抽象在 V0.1/V1 只会增加表面积而没有任何收益。所以本决策只做**基础配置能力**，
   多实例池仍然推到 V2。

5. **密钥不落库这一条不是洁癖，是合规要求。**
   `docs/security.md` 要求数据库敏感字段加密、传输 HTTPS。把 API Key 存进业务表，
   意味着任何一次数据库导出/备份泄露都等于密钥泄露。
   而"只存环境变量名"这个做法，让密钥的生命周期完全独立于数据库。

---

## 五、代价（必填）

1. **多了一张表 + 4 个接口 + 一套权限控制。**
   约 1.5—2 天的工作量（`docs/tasks.md` T59—T61），且 `config.update` 权限要纳入 RBAC。
2. **兼容层会掩盖厂商的真实差异。** 少数厂商在 `max_tokens` 语义、`system` 消息支持、
   流式结束标志上有细微差别。适配器统一掉之后，**这些差异在业务层看不到了** ——
   好消息是不用到处判断，坏消息是出问题时排查要往下钻一层。
3. **配置错误要在运行时才发现。** 存进数据库的配置没有编译期检查，
   填错 `base_url` 或 `provider` 只能靠 `model-test` 接口或第一次真实调用来暴露。
   → 所以 `model-test` 必须在保存时**强制跑一次**，不能让脏配置进库。
4. **改了配置会影响在跑的服务。** 换默认嵌入模型会导致新文档和旧文档向量维度/分布不一致。
   → 所以 `embedding_dim` 变更被设计成"新建一条配置 → 全量重建 → 切换默认"的流程，
   **不允许原地改**（`docs/data-model.md` 2.10 第 3 条硬约束）。
5. **少了一个"简历上的技术栈"**（LiteLLM 是行业常见词）。我接受这个代价。

---

## 六、复核条件

满足**任意一条**时重新评估：

- 需要接入的厂商出现**非 OpenAI 兼容**且无法用薄适配器覆盖的情况（例如某个必须有原生 SDK 的服务）
- `app/core/providers/` 下的适配器文件超过 6 个，说明"薄适配"这个假设已经不成立
- 需要"按知识库绑定不同模型组合"的真实需求出现（例如两个部门要求用不同模型），
  此时把 model_configs → knowledge_bases 的多对多绑定提上 V2
- 需要支持的模型数量超过 15 个，且手工维护 `model_configs` 明显吃力
- 出现"必须用一个独立网关服务才能满足"的合规或运维要求（例如统一做出口审计）

---

## 七、作为不懂技术的人，我只需要确认哪一点？

> 你只需要确认：**"模型配置做成数据库里可改的数据（不是代码里的常量），
> 代价是多写几天 CRUD 接口和一套权限。收益是你换模型做对比实验时，
> 不用改代码、不用重新发布，改完点一下测试就能用。"**
>
> 以及第二条：**"rerank 这一层我们只支持本地自建那一个，
> 不追求'随便换厂商'。因为很多厂商根本没有这个接口，追求多厂商适配是个无底洞，
> 而且云端 rerank 还不合规。"**
