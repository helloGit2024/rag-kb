# ADR-0006：部署用单机 Docker Compose，不上 K8s

- 状态：已采纳
- 日期：2026-10-21
- 决策人：我

---

## 一、背景

原需求写的是"V1 用 Docker Compose 单机，V2 上 K8s（企业级推荐）"，
并且提到"资源隔离：离线任务不能抢占在线问答的 GPU 资源"。

约束（来自 `docs/constraints.md`）：
- **不懂 Docker 命令，更不懂 K8s**
- 无运维支持
- 一台内网服务器：8 核 CPU / 32 GB 内存 / **无 GPU**
- 20 并发
- 服务器可长期占用，但只有一台

---

## 二、备选方案

| 方案 | 说明 | 好处 | 代价 |
|------|------|------|------|
| A. K8s | 容器编排平台 | 自动扩缩容、自动重启、滚动更新、资源隔离（requests/limits） | **学习曲线极陡**；单机 K8s 需要 k3s/minikube 且仍有大量概念；出问题时排查难度是我目前能力的 10 倍 |
| B. Docker Compose 单机 | 一个配置文件描述 5 个容器 | 一条命令起停；概念少（镜像/容器/volume）；日志用 `docker compose logs` 就看全了 | 不能自动扩缩容；没有自动故障转移；滚动更新要自己写脚本 |
| C. 裸机直接跑（systemd） | 不用容器 | 最简单 | 环境依赖难复现；换机器要重新配；版本回滚麻烦 |

---

## 三、决策

选定：**B（Docker Compose 单机）**，并在其上自己实现三条关键能力：
① 健康检查 + 自动重启（Compose 的 `restart: unless-stopped` + healthcheck）
② 离线任务并发限制（worker 内的信号量，`AGENTS.md` R10）
③ 一键回滚脚本（切换镜像 tag）

---

## 四、理由

1. **K8s 解决的问题，本项目都没有。**
   K8s 的核心价值是"在几十上百台机器上管理大量服务"。
   我只有一台机器、五个容器。**它解决的问题我不存在。**

2. **单机 K8s 是"用最高的复杂度换零收益"。**
   即使上 k3s，我也要理解 Pod / Service / Deployment / ConfigMap /
   Ingress / PVC 这一整套，以及为什么容器起不来、为什么 Service 找不到 Pod。
   **这些时间不会花在做功能上。**

3. **Compose 已经覆盖了必要的运维能力。**
   - 自动重启：`restart: unless-stopped`
   - 健康检查：`healthcheck` + 依赖顺序 `depends_on: condition: service_healthy`
   - 资源限制：`deploy.resources.limits`（CPU/内存）—— 这就能做到
     "离线任务不抢占在线资源" 的一半（另一半靠 worker 信号量）
   - 日志：`docker compose logs`

4. **"资源隔离"在单机无 GPU 环境下有更简单的解法。**
   原需求担心的是"离线任务抢占在线 GPU"。
   本项目无 GPU，实际冲突点只有 CPU 与内存：
   - worker 用信号量把并发限制在 2
   - worker 容器设 `cpus: 3.0`、`mem_limit: 8g`（给在线留出余量）
   - 入库任务支持"非高峰时段调度"（定时任务在凌晨跑全量重建）
   **这三条加起来，比 K8s 的 requests/limits 更直接，且不需要学新东西。**

---

## 五、代价（必填）

1. **没有自动故障转移。** 只能靠 `restart: unless-stopped` 重启容器；
   如果服务器本身宕机，服务就中断（直到我手动重启）。
   缓解：在公司的监控里加一条对 `/healthz` 的外部探测。
2. **更新时会短暂中断。** 没有滚动更新，`docker compose up -d --build` 期间服务不可用。
   缓解：更新安排在非工作时段；或先起新容器再切流量（单人项目不值得做）。
3. **不能水平扩容。** 20 并发已经验证够用；超过就只能换更强的机器。
4. **数据库和缓存也在同一台机器上**，单点故障。
   缓解：每日备份 + 每月恢复演练。
5. **将来如果真的要上 K8s，需要重写部署配置。**
   缓解：所有配置从环境变量读、镜像化、无本地状态依赖——
   这些习惯让迁移 K8s 时不至于重写业务代码。

---

## 六、复核条件

满足**任意一条**时重新评估：

- 同时在线用户 > 100，或 QPS 持续 > 5
- 需要 7×24 高可用（比如成为对外产品的一部分）
- 服务器从一台扩展到两台以上
- 团队演进到有专职运维

---

## 七、作为不懂技术的人，我只需要确认哪一点？

> 你只需要确认：**"K8s 是为管理'很多台机器上的很多服务'设计的。
> 我只有一台机器、五个容器，用 K8s 等于花 80% 的时间学一套用不上的概念。
> 代价是没有自动故障转移和滚动更新——我用'自动重启 + 每日备份 + 一键回滚脚本'来补，
> 这三件事我都能自己搞定。"**
