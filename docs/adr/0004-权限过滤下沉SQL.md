# ADR-0004：权限过滤下沉到 SQL，并在 chunk 上冗余 scope_key

- 状态：已采纳
- 日期：2026-10-21
- 决策人：我

---

## 一、背景

需求文档要求三级权限："知识库级权限""文档级权限""细粒度行级权限"。
但没写权限**绑定在哪张表的哪个字段上**。

如果不提前定，最自然的实现（也是 AI 会默认写出来的）是：

```python
hits = vector_search(q, limit=20)              # 先检索
visible = [h for h in hits if can_access(user, h)]  # 再过滤
```

这个写法的问题在 `docs/data-model.md` 第三节有详细对照。核心是两个：
① 越权内容已进入应用内存/日志/缓存；② 过滤后候选太少，召回质量断崖。

约束：
- 权限维度有三个：知识库、部门（文档密级 `dept:xxx`）、公开
- 一个用户可能同时命中多个范围（本部门 + 跨部门项目组 + public）
- 20 并发，30 万块

---

## 二、备选方案

| 方案 | 说明 | 好处 | 代价 |
|------|------|------|------|
| A. 应用层过滤 | 先检索 Top-N，再用 Python 筛 | 实现最简单；权限逻辑集中在一处 | **越权数据入内存/日志**；过滤后召回崩塌；N 要给很大才够 |
| B. 每权限一份独立索引 | 按 scope 建多个 collection/分区 | 检索时天然隔离，无需过滤 | 文档跨多个 scope 时要存多份；权限变更要重建索引 |
| C. chunk 冗余 scope_key + SQL 过滤 | 每个 chunk 上存一个 `scope_key`，检索 SQL 里带 `WHERE scope_key = ANY(...)` | 数据库保证不越权；过滤与检索同一次扫描；权限变更只需改授权表 | `scope_key` 是冗余字段，文档改密级时要批量回填 chunk |
| D. JOIN 权限表过滤 | chunk 不冗余，检索时 JOIN `documents` 取权限 | 无冗余，权限单一来源 | 每次检索多一次 JOIN，30 万块下影响延迟；SQL 更复杂 |

---

## 三、决策

选定：**C（chunk 上冗余 `scope_key`，权限条件写在检索 SQL 里）**

---

## 四、理由

1. **正确性优先级最高。** 越权是数据泄露事故，不是"体验问题"。
   方案 A 的根本缺陷是"越权数据已经进来了"——
   即使你筛掉了，它也可能已经写进了日志、进了缓存、被错误统计。
   **只有让数据库在检索阶段就查不到，才是可靠的。**

2. **召回质量。** 方案 A 下，如果你要保证过滤后还剩 5 条，
   就必须在检索时取 20—50 条。取少了会不够，取多了成本上升。
   方案 C 下，SQL 直接返回"有权范围内最相关的 5 条"，一条不浪费。

3. **性能比 D 好。** 冗余 `scope_key` + 复合索引 `(scope_key, kb_id)`，
   让过滤和向量排序在同一次索引扫描中完成，省掉 JOIN。

4. **权限变更的处理是可接受的。** 文档改密级时，
   只需 `UPDATE chunks SET scope_key=? WHERE doc_id=?`——
   一次性更新，且这个动作本来就应该走审计日志记录。

---

## 五、代价（必填）

1. **数据冗余。** `scope_key` 在同一个文档的所有 chunk 上重复存储。
   30 万块 × 平均 20 字节 = 约 6 MB。**完全可以接受。**
2. **一致性问题。** 如果某次代码路径改了 `documents.scope` 却没更新 `chunks.scope_key`，
   就会出现"文档说内部、chunk 说公开"的漏洞。
   缓解：① 改密级必须走一个统一的 service 方法，方法内同时更新两张表；
   ② 加一条定期一致性检查任务，比对两张表的不一致行数（应为 0）。
3. **`scope_key` 是字符串，不便于复杂权限表达式。**
   如果将来需要"研发部且是经理级才可见"这类组合条件，
   字符串方案要扩展成多个字段。**当前三级密级够用，超出了再改。**
4. **性能上，`ANY(:scope_keys)` 的索引利用率取决于数量。**
   如果一个用户被授予几十个 scope，查询计划可能退化。
   缓解：`scope_key` 数量在 20 以内时表现良好；超出时考虑改成位图或权限表 JOIN。

---

## 六、复核条件

满足**任意一条**时重新评估：

- 单个用户的 `scope_key` 数量普遍 > 20
- 出现需要"组合条件权限"（部门 + 职级 + 项目）的需求
- 一致性检查任务发现不一致行数长期 > 0（说明更新路径有漏洞，先修漏洞再评估方案）
- 检索延迟 P95 中，权限过滤导致的部分 > 100ms

---

## 七、作为不懂技术的人，我只需要确认哪一点？

> 你只需要确认：**"权限过滤放在数据库里做（而不是查出结果再筛掉），
> 是让'用户看不到不该看的文档'从'靠我写对代码'变成'靠数据库本身保证'。
> 代价是每个文档块上多存一个权限标记，改文档密级时要同步更新——而这本来就应该走一个统一的入口。"**
