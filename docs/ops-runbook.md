# 运维手册（ops-runbook.md）

> 原需求列了"监控、日志、告警"的模块清单，但没有写**阈值是多少、超了怎么办、谁去做**。
> 告警的价值不在于"能告警"，而在于**你凌晨两点被叫醒时知道该干什么**。
>
> **单人项目的运维原则：能自动处理的绝不叫人。**
> 所以这份手册给每个场景都先写"自动动作"，再写"人工动作"。

## 一、监控指标与阈值

### 1.1 业务指标（Grafana 大盘）

| 指标 | 正常范围 | 警告阈值 | 严重阈值 | 数据来源 |
|------|---------|---------|---------|---------|
| QPS | — | — | — | 应用埋点 |
| 成功率 | ≥ 99% | < 98% | < 95% | 应用埋点 |
| 端到端 P95 延迟 | < 3.5s | > 5s | > 8s | 应用埋点 |
| 检索 P95 延迟 | < 200ms | > 300ms | > 600ms | 应用埋点 |
| **拒答率** | 8%—25% | < 5% 或 > 35% | < 3% | 应用埋点 |
| **负反馈率** | < 10% | > 15% | > 25% | 反馈接口 |
| 单次成本 | < ¥0.025 | > ¥0.03 | > ¥0.05 | LLM 网关 |
| 月度累计成本 | — | ≥ 80% 预算 | ≥ 90% 预算 | LLM 网关 |
| 评估任务失败率 | 0% | > 10% | > 30% | 任务队列 |
| **SQL 通道占比**（V2） | 10%—40% | > 60% | < 2%（通道形同虚设） | 应用埋点（`query_logs.channel`） |
| **路由准确率**（V2） | ≥ 0.90 | < 0.85 | < 0.75 | 线上抽检 + `nl2sql_logs` |
| **SQL 校验未通过率**（V2） | < 30% | > 50% | > 70% | `nl2sql_logs.reject_reason` |
| **SQL 超时率**（V2） | 0% | > 5% | > 15% | 数据源埋点 |
| SQL 通道单次成本（V2） | < ¥0.05 | > ¥0.07 | > ¥0.12 | LLM 网关 |
| SQL 通道 P95 延迟（V2） | < 6s | > 8s | > 12s | 应用埋点 |

> **"拒答率"是一个双向告警指标**：
> 它突然变低 = 系统开始乱答（幻觉爆发）；
> 它突然变高 = 检索坏了或阈值过严（大量误拒）。
> 只设单向告警，你会漏掉一半的故障。这与 `evals/README.md` 里
> "拒答正确率和误拒率必须成对"是同一个道理。

> **（V2）"SQL 校验未通过率"也是一个会被误读的指标。**
> 它高（> 50%）**通常不是故障**，而是**语义层覆盖度不够**——
> 用户问的东西你还没在 `semantic_layer.yaml` 里声明。
> 所以它的处置动作是"**去看 `reject_reason` 排行、补语义层**"，
> 而不是"去修校验逻辑"（校验逻辑拦得对，这是它在正常工作）。
> 反过来，它**突然变成 0%** 才是危险信号：说明校验可能被绕过了，
> 或者 `reject_reason` 没在写日志——**一个从不拒绝的系统，通常不是一个好系统。**

> **（V2）"SQL 通道占比"是双向的**：
> 太高（> 60%）= 路由偏向 SQL，文档能答的题也被塞进 SQL，静默失败风险上升；
> 太低（< 2%）= 通道形同虚设，说明路由过于保守，或者语义层太薄没人用得上。
> 这两个方向的处理动作相反（一个收紧路由、一个补语义层），
> 所以必须**同时看高低两端**。

### 1.2 底层资源指标

| 指标 | 正常 | 警告 | 严重 |
|------|------|------|------|
| CPU 使用率（15 分钟均值） | < 60% | ≥ 80% | ≥ 92% |
| 内存使用率 | < 70% | ≥ 85% | ≥ 93% |
| 磁盘使用率 | < 70% | ≥ 85% | ≥ 92% |
| PostgreSQL 连接数 | < 60 | ≥ 100 | ≥ 140 |
| Redis 内存 | < 200MB | ≥ 500MB | ≥ 800MB |
| 任务队列积压 | < 50 | ≥ 300 | ≥ 1000 |
| 模型接口错误率 | 0% | > 5% | > 20% |
| 容器重启次数（1h） | 0 | ≥ 3 | ≥ 10 |

## 二、告警规则与处置（AlertManager）

### A1 服务宕机 / 健康检查失败

- **触发**：`/healthz` 连续 3 次失败（间隔 30s）
- **自动动作**：Docker 重启该容器（最多 3 次）
- **人工动作**：
  1. `make logs | tail -200` 看最后报错
  2. 若与数据库连接有关 → 检查 PostgreSQL 容器与磁盘
  3. 若与模型服务有关 → 检查本地推理服务进程
  4. 无法 15 分钟内恢复 → `make rollback`

### A2 接口错误率飙升

- **触发**：5 分钟内 5xx 占比 > 5%
- **自动动作**：无
- **人工动作**：先看 Grafana 上错误集中在哪个接口，再决定：
  - 集中于 `/query` → 多为模型服务问题 → 检查 A3
  - 集中于上传相关 → 多为存储问题 → 检查 MinIO

### A3 模型接口持续超时 / 失败

- **触发**：模型接口错误率 > 20%，持续 2 分钟
- **自动动作**：
  1. LLM 网关自动切换备用模型（已有）
  2. 备用模型也失败 → **自动打开全局降级开关**（`POST /admin/degrade`），
     改为"只返回检索片段"，并在响应中标记 `degraded=true`
- **人工动作**：
  1. 确认降级已生效：`curl -s localhost:8000/api/v1/admin/stats | jq .degraded`
  2. 排查是密钥过期、额度耗尽还是下游故障
  3. 恢复后在**内部群/自己的记录里注明**，并关闭降级开关

> **降级开关为什么必须存在**：模型服务是最容易挂的外部依赖。
> 没有它，模型一挂全站 500；
> 有它，用户至少还能拿到检索到的原文片段——**产品的可用性下限被抬高了**。

### A4 本地嵌入模型不可用

- **触发**：健康检查中 `embedding_model=down`，或入库任务大量失败
- **自动动作**：暂停从任务队列取新的入库任务（避免任务全变失败）
- **人工动作**：重启本地推理服务；检查是否被离线任务占满 CPU
  → 确认 `app/workers` 的并发信号量是否生效（`AGENTS.md` R10）

### A5 向量库 / 数据库连接异常

- **触发**：PostgreSQL 连接池耗尽或查询超时
- **自动动作**：拒绝新请求并返回 503（优于排队到全站卡死）
- **人工动作**：检查慢查询日志；若是 pgvector 索引膨胀，执行 `VACUUM ANALYZE`

### A6 文档解析任务大量失败

- **触发**：30 分钟内解析失败率 > 30%
- **自动动作**：无
- **人工动作**：
  1. 查 `GET /api/v1/documents?status=failed` 看失败原因分布
  2. 若集中在某类文件 → 可能是解析器 bug，收集 3 个样本做回归用例
  3. 若是编码问题 → 补充编码探测与转换

### A7 存储占用过高

- **触发**：磁盘 ≥ 85%
- **自动动作**：清理 30 天前的任务日志与临时文件
- **人工动作**：检查 MinIO 是否有大文件堆积；评估是否需要归档历史 query_logs

### A8 成本超预算

- **触发**：月度累计 ≥ 80%
- **自动动作**：≥ 90% 时自动降级为仅检索（AC-17）；发送通知
- **人工动作**：检查是否有异常高频用户（看 `query_logs` 按用户聚合），
  调低单用户限流阈值

---

### A9 业务数据源连接失败（V2）

- **触发**：`SQL_CHANNEL_DSN` 连接连续 3 次失败，或 `nl2sql_logs` 出现 `datasource_error`
- **自动动作**：**只关闭 SQL 通道**，`/query` 自动回落 `doc` 通道（其余功能不受影响）
- **人工动作**：
  1. 确认回落是否生效：`curl -s localhost:8000/api/v1/admin/stats | jq .sql_channel`
  2. 检查只读账号是否被改密码 / 被回收权限
  3. 检查业务库网络可达性与最大连接数
  4. 恢复后先跑 `make eval-sql` 确认口径没漂

> **为什么数据源挂了不整体降级**：SQL 通道是**可选能力**。
> 它挂了不该拖垮文档通道——文档通道才是 V1 的主力。
> 所以这里的自动动作是**局部关闭**，而不是 A3 那种全局降级。
> 这条差异必须写清楚，否则 AI 很可能"顺手"把它接到全局降级开关上。

### A10 SQL 超时率升高（V2）

- **触发**：SQL 超时率 > 5%，持续 10 分钟
- **自动动作**：无（超时会在 `statement_timeout_ms` 处被数据库自己砍掉，不会拖垮服务）
- **人工动作**：
  1. 从 `nl2sql_logs` 捞超时的 SQL，看是否集中在某张表 / 某个指标
  2. 若某指标必然超时 → 该指标**需要预先聚合成物化视图**，不要每次实时算
  3. 若普遍偏慢 → 检查业务库是否在跑批（`T+1` 数据通常在凌晨刷新）

### A11 `unknown_object` 突增（V2）

- **触发**：`nl2sql_logs.reject_reason='unknown_object'` 的占比 24 小时内翻倍
- **自动动作**：无
- **人工动作**：
  1. 拉 `unknown_object` 排行（按出现次数）—— 这是一个**可运营指标**，不是故障
  2. 按频次从高到低补 `semantic_layer.yaml`（加 metric / 加 enum / 加 table）
  3. 补完**必须**跑 `make eval-sql`，确认没有把已有题的口径改坏

> **为什么这不是告警而是"待办"**：`unknown_object` 高**不影响正确性**——
> 没覆盖的东西系统会拒答，拒答是安全行为。
> 它的意义是"用户在问什么、你还没准备好"，
> 所以处置方式是**定期补充**，而不是**立即止损**。

### A12 路由准确率跌破线（V2）

- **触发**：抽检（每日取 20 条线上问答人工判通道）准确率 < 0.85
- **自动动作**：无
- **人工动作**：
  1. 看错分的方向：`doc→sql`（静默失败风险高）还是 `sql→doc`（只是少了个能力）
  2. 若集中在 `doc→sql`，**先把路由阈值收紧**（`confidence` 门槛上调），宁可少走 SQL
  3. 用错的样例补 `golden_set_sql.yaml` 的 `route_to_doc` 题（见 `evals/sql/README.md` 第八节）
  4. **不要**直接去改生成提示词——路由错和生成错是两回事（见 `evals/attribution.md` 9.2）

> **为什么 H24（路由准确率）权重高于 H25（执行准确率）**：
> SQL 写错会**报错或返回 0 行**，是可见失败，用户会重问；
> 路由错会产出"语法完美、执行成功、数字真实、答非所问"的答案——
> 这是**静默失败**，用户不会发现，而且会拿它去汇报。
> 所以宁可让 SQL 少干点活（收紧路由），也不能让它答错范围。

## 三、故障处置总流程（第一反应清单）

```
发现异常
  │
  ├─ 1. 先看大盘（30 秒）        → 是全面故障还是局部？
  │
  ├─ 2. 是模型相关吗？
  │     └─ 是 → 打开降级开关（10 秒生效），先止损，再排查
  │
  ├─ 3. 是本次上线引入的吗？（看最近一次部署时间）
  │     └─ 是 → make rollback（目标 < 5 分钟）
  │
  ├─ 4. 数据错了吗？（越权 / 泄露 / 数字错误）
  │     └─ 是 → 优先止血：直接停掉服务，而不是"边跑边修"
  │           ★ 数据类故障比可用性类故障严重得多
  │           ★（V2）若错在 SQL 通道 → 先 `POST /admin/sql-channel` 关闭通道
  │                （只关 SQL，文档通道继续用），再排查口径/权限
  │
  └─ 5. 记录：时间、现象、影响范围、处理动作
        （写进 docs/experiments/ 或单独的故障记录）
```

> **第 4 条最重要**：可用性故障（服务挂了）用户会等你；
> 数据故障（越权、泄露、给出错误数字）一旦被看到，信任就没了。
> **遇到数据类问题，宁可停服。**

## 四、回滚

### 4.1 应用回滚

```bash
# 镜像标签 = git commit 短哈希，回滚就是切回上一个标签
make rollback
# 实际执行：docker compose up -d 时指定上一版镜像 tag
```

**回滚时间目标：< 5 分钟。必须真实演练过至少一次。**
没有演练过的回滚，在真出事时通常要 1 小时。

### 4.2 数据库回滚

| 情况 | 能回滚吗 | 做法 |
|------|---------|------|
| 加了字段 | ✅ 能 | `alembic downgrade -1` |
| 加了索引 | ✅ 能 | 同上 |
| **删了字段** | ❌ **不能** | 数据已丢失。所以 `AGENTS.md` R8 禁止"删字段 + 改代码"同一次发布 |
| **改了字段含义** | ❌ 不能 | 同上，必须拆两次发布 |

**纪律：每次迁移前问自己一句"如果 5 分钟后要回滚，数据还在吗？"**

### 4.3 数据恢复

```bash
# 恢复到最近一次全量备份（RTO 目标 2 小时）
docker compose exec postgres pg_restore -d kb /backup/latest.dump
```

**每月做一次恢复演练**（恢复到临时库并验证行数）。
没演练过的备份等于没有备份——这是运维里最常见的自欺。

| 对象 | 方式 | 频率 | 保留 | 恢复演练 |

## 六、日常检查清单

### 每日（5 分钟）

- [ ] 看大盘：成功率、P95 延迟、拒答率、成本
- [ ] 看失败文档列表，有新失败就记录原因
- [ ] 看负反馈列表，挑 1—3 条真实失败案例
- [ ]（V2）看 SQL 通道：占比、校验未通过率、超时率（**重点看有没有"该走文档却走了 SQL"**）

### 每周（30 分钟）

- [ ] 跑一次 `make eval`，与上周对比
- [ ] 把本周的线下失败案例补进评估集（**失败案例驱动**）
- [ ] 检查磁盘、备份是否成功
- [ ] 看有没有新的攻击尝试记录
- [ ]（V2）跑 `make eval-sql`（含 `make seed-sql` 起临时库），看路由/执行两项指标
- [ ]（V2）拉 `unknown_object` 排行，补 3—5 个最高频的语义层条目

### 每月（2 小时）

- [ ] **恢复演练**：从备份恢复到一个临时库，验证数据完整
- [ ] **回滚演练**：故意部署一个坏版本，走一遍回滚流程
- [ ] 成本复盘：本月总花费、单次均成本、是否有异常用户
- [ ] 依赖更新与漏洞扫描
- [ ] 过期缓存与日志清理
- [ ]（V2）复核 `semantic_layer.yaml`：有没有指标被"顺手"放宽了 `scope_mode`；
      `denylisted_columns` 是否仍覆盖所有敏感字段

## 七、上线检查清单（每次发布前）

- [ ] `docs/quality-gates.md` 的硬门禁全部通过
- [ ] 数据库迁移已验证可回滚（涉及删字段/改含义的**必须拆两次发布**）
- [ ] 已确认本次改动**没有**触碰权限过滤逻辑；如有，越权测试必跑
- [ ] 提示词改动已单独提交（类型 `prompt:`）
- [ ] 备份已完成且是最近的
- [ ] 知道怎么回滚，且回滚命令在手边
- [ ] 灰度：先在 1—2 个内部账号上验证，再扩大
- [ ]（V2）若本次改动涉及语义层（`semantic_layer.yaml`）：
      ① 已单独提交（类型 `semantic:`）并记入 `semantic_layer_versions`；
      ② `scope_mode` 没有被"顺手"放宽；
      ③ 跑过 `make eval-sql`，路由准确率与执行准确率都没有跌破线
- [ ]（V2）SQL 通道安全测试（`security.md` 第 11—16 条）全通过，**尤其第 13 条注释绕过**
