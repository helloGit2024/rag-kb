# 质量门禁（quality-gates.md）

> 指标体系如果不落成"门禁"，就只是一份好看的报告。
> 门禁的含义是：**不达标就禁止合并/发布**——而不是"不达标时提醒一下"。
>
> **为什么必须区分硬门禁和软门禁**：
> 如果把所有指标都设成硬门禁，会出现两个问题：
> ① 指标互相打架（提升忠实度会让系统更保守，从而降低回答率），导致没人能通过；
> ② 你会开始绕过门禁——比如为了过覆盖率把断言删掉。
> 一个被频繁绕过的门禁，不如没有门禁。

---

## 一、硬门禁（不通过 = 禁止合并到 main）

| # | 检查项 | 阈值 | 对应验收标准 | 怎么跑 |
|---|-------|------|------------|-------|
| H1 | 单元 + 集成测试 | 全部通过 | — | `make test` |
| H2 | 测试覆盖率 | ≥ 70%（核心模块 ≥ 85%） | — | `make test`（带 `--cov-fail-under`） |
| H3 | 类型检查 | mypy 零错误 | — | `make lint` |
| H4 | 代码规范 | ruff / eslint 零 error | — | `make lint` |
| H5 | **密钥扫描** | 无任何疑似密钥 | `AGENTS.md` R1 | `make scan` |
| H6 | **越权测试** | 全部通过，0 泄漏 | AC-05 | `make test -k permission` |
| H7 | **拒答正确率** | ≥ 0.90 | AC-09 | `make eval` |
| H8 | **误拒率** | ≤ 0.05 | AC-09 | `make eval` |
| H9 | **Recall@5 / MRR** | Recall@5 ≥ 0.85 且相对基线下降 ≤ 2%；MRR ≥ 0.70 | AC-07 | `make eval-compare` |
| H10 | 提示词是否为独立文件 | 是（不允许写在 .py 里） | `AGENTS.md` R4 | 代码审查 |
| H11 | 数据库迁移是否可回滚 | 已标注并验证 | `AGENTS.md` R8 | 人工审查 |

> **H6/H7/H8/H9 是本项目特有的硬门禁。**
> 普通软件项目没有这几条，但 RAG 项目必须有——
> 因为它们的失败模式是"静默的"：系统不会报错，只会悄悄开始编造或悄悄开始泄漏。

## 二、软门禁（不通过 = 必须在合并说明里解释）

| # | 检查项 | 目标 | 不达标时怎么办 |
|---|-------|------|--------------|
| S1 | 忠实度 Faithfulness | ≥ 0.85 | 记录原因，列入下个迭代的首要任务 |
| S2 | 引用准确率 | ≥ 0.90 | 同上 |
| S3 | P95 端到端延迟 | < 5 秒 | 若上升 > 20%，必须说明 |
| S4 | 首字延迟（流式） | < 1.5 秒 | V1 生效 |
| S5 | 单次问答成本 | < ¥0.03 | 若上升 > 30%，必须说明 |
| S6 | 测试覆盖率 | 上升或持平 | 下降需说明 |
| S7 | 新增依赖数量 | 0 | 每新增 1 个必须写理由 |
| S8 | 单次改动文件数 | ≤ 8 | 超过说明任务拆得不够细 |

## 三、分版本的门禁强度

| 版本 | 硬门禁范围 | 说明 |
|------|-----------|------|
| V-1 骨架 | 仅 H1、H3、H5 | 还不存在评估集，先保证代码能跑 |
| V0.1 | H1—H11 全部 | 从有评估集那一刻起，全部生效 |
| V1 | 全部 + 压测 + 回滚演练 | 见下方 |
| V2 | 全部；**启用 SQL 通道时再追加 H24—H26** | 见下方「V2 追加的硬门禁」 |

**V1 追加的硬门禁**

| # | 检查项 | 阈值 |
|---|-------|------|
| H12 | 并发压测（20 用户） | 无 500；P95 上升 ≤ 2 倍 |
| H13 | 回滚演练 | 从触发到服务恢复 < 5 分钟，且**真实执行过** |
| H14 | 审计日志不可修改 | 尝试 UPDATE 被拒绝 |
| H15 | 文档删除全链路清理 | 删除后全库搜索其任意片段为 0 结果 |
| H16 | 备份恢复演练 | 能在 2 小时内从备份恢复服务 |
| H17 | 降级开关 | 10 秒内全站生效 |
| H18 | 依赖漏洞扫描 | 无高危 |
| H19 | **模型配置可管理** | 通过接口改默认模型后，新请求的 `model_used` 随之改变，且**无需重新部署**（AC-20） |
| H20 | **密钥不落库** | 全表 + 日志按密钥特征串检索 0 命中；密钥明文填入 `api_key_ref` 被服务端拒绝（AC-21） |
| H21 | **评估可复现** | 跑评估前 checksum 校验通过（不一致 → 409 `STALE_DATASET`）；每条运行都存了 `git_commit` + `config_snapshot`（AC-22） |
| H22 | **未确认的数据集不得进门禁** | `unconfirmed_count > 0` 的数据集发起评估 → 409 `DATASET_NOT_ACTIVE`（AC-23） |
| H23 | **归因结论必须带依据** | 只填 `attribution` 不填 `attribution_basis` → 422；`attribution_confirmed` 为空的行不出现在任何归因汇总里（AC-24） |

> **为什么 H19/H20 是硬门禁**：它们各自对应一个"静默失败"。
> H19 失败时，系统看起来一切正常，但你其实**无法做模型对比实验**——
> 因为每次换模型都要改代码，你会因为麻烦而放弃；
> H20 失败时，系统也一切正常，直到某天有人导出了一次数据库。
>
> 这两条的验收动作都很简单（改配置看行为、搜特征串），
> 完全不需要读代码——**这正是"硬门禁"该有的形态**。

> **H21—H23 是同一类"静默失败"，而且更隐蔽**：
>
> | 门禁 | 失效时你会看到什么 |
> |------|------------------|
> | H21 | 一切正常，只是某个数字无法解释，你会花半天找原因，最后可能得出**错误结论** |
> | H22 | 一切正常，门禁也"通过"了 —— 但它考的是 AI 自己出的题、自己定的答案 |
> | H23 | 一切正常，报告很漂亮；三个月后你无法回答"当初为什么判成检索问题" |
>
> 三条的验收动作同样不需要读代码：改个文件看是否被拒、看"未确认 N 条"是否一致、发一次残缺请求看是否被拒。

**V2 追加的硬门禁（仅当启用 SQL 通道时生效）**

| # | 检查项 | 阈值 |
|---|-------|------|
| H24 | ★ **路由准确率** | ≥ 0.90（AC-27） |
| H25 | ★ **执行准确率 EX（比结果集，不比 SQL 文本）** | ≥ 0.80，且相对基线下降 ≤ 2%（AC-28） |
| H26 | ★ **SQL 只读 + 聚合范围标注** | 12 条攻击/越界输入**全部拦住**且无一条产生写操作；`scope_mode=own` 的答案**全部**带范围标注（AC-29、AC-30） |

> **为什么 H24—H26 必须是硬门禁，而不是"上线前检查一下"**：
> 它们各自对应一个**静默失败**：
>
> | 门禁 | 失败时会怎样 |
> |------|------------|
> | H24 路由 | 一个语法完美、执行成功、数字真实存在、但答的不是用户问题的答案。**没有引用可点、没有原文可对，无人能发现** |
> | H25 执行 | 数字看起来完全正常，你要到财务对账时才知道少算了一半 |
> | H26 只读 | 系统一切正常，直到某次注入真的产生了 `DELETE`；或用户拿着"销售部平均"当"全公司平均"去汇报 |
>
> 三条的验收动作都很土：看一个准确率的数、跑 12 条 SQL、检查答案里有没有
> "基于你有权访问的 N 条记录"这句话。**完全不需要读代码 —— 这正是"硬门禁"该有的形态。**
>
> **注意 H24 的权重高于 H25**：写错 SQL 会报错或返回 0 行（可见失败）；路由错不会。
> 所以**先修路由，再修生成** —— 顺序反了会白花很多时间。
>
> **还有一条软要求（不进硬门禁，但必须看）**：H24—H26 全部达标之后，
> 还要确认**文档通道的指标相对 V1 没有下降**（H7—H9）。
> 因为路由错会把本该走文档的题引到 SQL 上 —— 那部分损失**记在文档通道的账上**。

## 四、CI 流水线编排

```yaml
# .github/workflows/ci.yml（示意，AI 可直接实现）
name: ci
on: [push, pull_request]

jobs:
  quality:
    steps:
      - run: make lint          # H3 H4
      - run: make scan          # H5
      - run: make test          # H1 H2 H6
      - run: make migrate && make migrate-down && make migrate   # H11 可回滚验证
      - run: make eval          # H7 H8 H9 + S1—S5
      - name: 对比基线，指标下降则失败
        run: make eval-compare   # H21（含 checksum 校验）
      - run: make eval-attribute # 只跑检索路径，产出归因候选（不入门禁，供人工确认）
      # ── V2：启用 SQL 通道后追加 ──────────────────────────────
      - run: make seed-sql       # 建临时库 + 灌 evals/sql/seed.sql（结果可复现的前提）
      - run: make eval-sql       # H24 H25（比结果集，不比 SQL 文本）+ SQL 侧拒答率
      - run: make test -k sql_safety   # H26（12 条攻击/越界输入）
```

**关键点：故意提交一个坏改动，确认 CI 真的拦住了它。**
这一步一定要试。很多人的 CI 是"装饰性"的——
写得很好看，但从没实际拦住过任何东西。

测试方法：
1. 把 `evals/golden_set.yaml` 里某条题的 `should_refuse` 改成错的
2. 推一个提交
3. 看 CI 是否变红

如果没变红，说明评估根本没接进门禁——那 `make eval` 只是一条装饰性的命令。

**V2 追加一个：故意把某条题的 `expected_channel` 从 `doc` 改成 `sql`**，确认 H24 变红。
理由同上 —— 路由准确率最容易退化成一个"报表上的数字"，
而它恰恰是 SQL 通道里权重最高的门禁（H24 > H25）。

## 五、门禁与"完成定义"的关系

`AGENTS.md` 的完成定义（DoD）是**你让 AI 遵守的**；
本文件的门禁是**CI 强制执行的**。

两者必须一致。如果 DoD 里写了某条、门禁里没有，AI 就会慢慢忽略它；
如果门禁里有某条、DoD 里没写，AI 会在被拦住时感到意外，然后想绕过。

**所以这两份文件要一起改。**
