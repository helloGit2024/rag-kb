# 术语表（glossary.md）

> **为什么需要这份文件**：AI 会按字面理解术语，然后写出错误的逻辑。
> 写进去一次，以后它就不会再误解——这是投入产出比最高的一份文档。
>
> 原需求文档里直接出现了 RAPTOR、CRAG、Self-RAG、ColBERT、HyDE、RAGAS
> 等术语但没有解释，对非技术读者不友好。这里补齐。

## 一、RAG 核心术语（用大白话）

| 术语 | 大白话解释 | 类比 | 在本项目里指什么 |
|------|-----------|------|----------------|
| **分块 / Chunking** | 把长文档切成一小组文本片段 | 把一本书拆成一页一页，方便翻到相关那页 | 默认 512 字一块、重叠 64 字 |
| **Chunk（文档块）** | 切分后的最小检索单位 | 书的"一页" | 检索、引用、权限都绑定在 chunk 上 |
| **向量 / Embedding** | 把文字转成一串数字，用来比较语义相似度 | 给每句话做"语义指纹" | bge-m3 输出 1024 维向量 |
| **稠密向量检索** | 按语义相似度找 | 找"意思相近"的段落 | V0.1 唯一的检索方式 |
| **BM25 / 稀疏检索** | 按字词精确匹配找 | 图书馆按书名/编号查目录 | V1 加入，专治专有名词、编号、条款号 |
| **混合检索 Hybrid** | 上面两种各查一遍 | 两个人分别找，再对答案 | V1 的核心升级 |
| **RRF（倒数排名融合）** | 把多路检索结果按"排名"合并 | 几个评委各自排名次，不比较原始分数 | V1 融合方式，不需要调权重 |
| **重排序 / Rerank** | 对初筛结果再精排一次 | 海选后复赛 | V1：Top-20 → Top-5 |
| **查询改写 / Query Rewrite** | 把口语问题改成检索友好的查询 | 把"年假咋算"改成"员工年假天数规定" | V1，规则 + 小模型 |
| **HyDE** | 先让模型编一个"假答案"，再用它去检索 | 先猜个大概，再按猜测去找 | **V2 才考虑，现在不做** |
| **忠实度 / Faithfulness** | 答案里有多少内容是编造的 | 有没有照着材料说话 | 核心质量指标，目标 ≥ 0.85 |
| **拒答 / Refuse** | 知识库里没有时老实说不知道 | — | 固定句式 + `refused=true` |
| **误拒** | 明明有答案却说不知道 | — | 必须 ≤ 0.05，与拒答正确率成对约束 |
| **引用绑定 / Citation** | 把答案里的编号映射回真实原文段落 | 论文的参考文献 | 决定"可不可信"，是全项目最重要的一环 |
| **父子块** | 小块用来检索（准），大块喂给模型（全） | 用目录页找章节，再读整章 | **V2 再考虑**，V0.1 用固定大小块 |
| **RAGAS** | 一套自动算 RAG 质量分数的工具库 | — | V0.1 直接用它的指标定义，V2 再做平台 |
| **LLM-as-Judge** | 用一个模型给另一个模型的答案打分 | 请另一个老师批卷 | 评估集自动评分方式（见 `evals/judge-prompt.md`） |
| **提示词注入** | 用户或文档里藏"忽略以上指令"，试图操控模型 | 有人在申请表里夹一张假公文 | 直接注入 + **间接注入**（藏在文档里）两类都要防 |

## 二、只出现在原需求、本项目明确不做的术语

| 术语 | 含义 | 为什么本项目不做 |
|------|------|----------------|
| **RAPTOR** | 把文档递归聚类成树状摘要，用摘要层辅助检索 | 建树成本高、调参复杂，V0.1—V1 用不上 |
| **ColBERT** | 一种细粒度（词级）向量检索方式 | 索引体积是普通向量的 10 倍以上，无 GPU 环境不划算 |
| **GraphRAG** | 把文档抽成知识图谱再检索 | 建图 Token 成本是普通入库的 10—100 倍，V2 试点前必须先算账 |
| **Self-RAG** | 模型自己判断"要不要检索、答案自不自洽" | 增加 1—2 次额外模型调用，延迟与成本翻倍 |
| **CRAG** | 检索质量差时自动纠正或放弃检索 | 与 Self-RAG 类似，V2 再评估 |
| **Agentic RAG** | 让 Agent 自主多步检索与工具调用 | 流程不可预测、评测困难，单人项目风险过高 |

> **这一节存在的意义**：当 AI 或同事说"我们加个 GraphRAG 吧"，
> 你可以指着这张表说"知道它是什么，也知道为什么现在不做"。

> **⚠️ 一处已被推翻的判断（留在此处，不要删）**：这张表原先有一行 **Text-to-SQL**，
> 写的是"本项目没有结构化数据查询需求，明确不做"。
> **V2 已改为做**（`docs/adr/0009`），但**是带前置条件的做**——
> 语义层先于提示词、路由优先于生成、五道闸门一个不少。
> 保留这段是为了说明：**"现在不做"和"永远不做"是两回事。**
> 当初判断"不做"的理由（单人维护、预算低）**并没有消失**，
> 所以它没有变成"排到就做"，而是变成了"前置条件满足才做"。
> 术语见下一节。

## 三、SQL 通道术语（V2）

| 术语 | 大白话 | 类比 | 在本项目里指什么 |
|------|-------|------|----------------|
| **Text-to-SQL / NL2SQL** | 把"上个月花了多少"这种话，变成一条数据库查询语句 | 把口语翻成"库管员能听懂的单子" | V2 的**第六条能力**，与文档通道并列（`docs/text-to-sql.md`） |
| **双通道 / 通道（channel）** | 同一个提问入口，内部走两条路：查文档 or 查数据库 | 一个前台，两个办事窗口 | `query_logs.channel` = `doc` / `sql` / `hybrid`；**默认 `doc`** |
| **路由（router）** | 判断这道题该走哪条通道 | 分诊台护士 | 三段式：规则 → 分类 → 兜底回落 `doc`；**它比生成更重要** |
| **语义层 / Semantic Layer** | 一份"业务口径说明书"，告诉模型：有哪些指标、每个指标怎么算、哪些字段不许碰 | 给新员工的《取数口径手册》 | `config/semantic_layer.yaml`，**走 Git 不进数据库**；是 SQL 通道**唯一的对象来源** |
| **指标（metric）** | 一个有名有姓的业务数字，如"培训支出" | 报表上的一个格子 | 语义层里的 `metrics` 条目，含 `sql` 片段 + `where` + `time_column` + `scope_mode` |
| **口径** | 同一个指标名，可能有好几种算法 | "上个月"到底是按提交日还是结算日？含不含税？含不含已作废？ | 四个变量（时间字段 × 含税 × 状态 × 跨期）可组合出多个**都执行正确**的不同数字 |
| **`scope_mode`** | 这个指标该按"我的权限范围"算，还是按全公司算 | 是"我部门的数"还是"全公司的数" | `own`（默认，受行级权限约束）/ `global`（仅限不算敏感的计数类指标） |
| **路由准确率** | 该走文档的题有没有走文档 | 分诊有没有分错科 | **权重高于执行准确率**（H24 ≥ 0.90）——因为路由错是**静默失败** |
| **执行准确率 / EX（Execution Accuracy）** | 生成的 SQL 跑出来的**结果集**，和标准答案是不是一样 | 答案对不对，不看解题过程 | H25 ≥ 0.80；**比结果集，不比 SQL 文本**（列序/行序/列名都不参与比对） |
| **结果集比对** | 只比"查出来的那张表"，不比"那条 SQL 长什么样" | 对答案，不对草稿 | 数值容差 `1e-6`；只有声明了 `result_order_matters` 的题才比行序 |
| **五道闸门** | SQL 执行前的五层安检 | 机场安检 | 只读账号 → 解析器结构校验 → 对象白名单 → 强制 LIMIT → 超时配额 |
| **`unknown_object`** | 模型想查的东西，语义层里没声明 | 你要的药，药房没有 | **不是错误，是待办**——按排行补语义层，从空开始按需加 |
| **拒答原因码 / `refused_reason`** | 为什么没回答 | 挂号单上的退号理由 | `doc_no_match` / `schema_no_match` / `scope_denied` / `unsafe_sql` |

> **这一节存在的意义**：SQL 通道最容易犯的错，是把它当成"给 RAG 加个功能"。
> 实际上它引入了一整套新概念（语义层、路由、口径、EX），
> 而其中**最反直觉的一条**是：**路由比生成重要**。
> 生成错会报错/返回空（可见失败）；路由错会给出一个"看起来完全正确"的错答案（静默失败）。

## 四、工程术语（给非技术人的解释）

| 术语 | 大白话 | 在本项目里指什么 |
|------|-------|----------------|
| Docker / 容器 | 把你的程序 + 它需要的环境打包成一个"盒子"，换台机器也能跑 | `docker compose up` 一条命令起全部服务 |
| Docker Compose | 用一个配置文件描述"要起哪几个盒子、怎么连" | 我们的部署方式 |
| K8s | 管理几十上百个容器集群的系统 | **不用**，单人维护不了 |
| API | 程序之间说话的接口 | 前端的每个操作对应一个 API |
| OpenAPI / Swagger | 一份"接口说明书"，写明每个接口要什么、返回什么 | `docs/openapi.yaml` |
| 契约冻结 | 接口说明书定下来就不许随便改 | 改了就要同步改前端和测试 |
| 迁移 / Migration | 数据库结构变化的记录文件 | 可回滚，但**已经改掉的数据不能回滚** |
| CI | 每次提交自动跑测试、检查代码 | `.github/workflows/ci.yml` |
| 门禁 / Gate | 不达标就禁止合并 | `docs/quality-gates.md` |
| 灰度 | 先让 5% 的人用新版本，没问题再全量 | V1 上线方式 |
| 回滚 | 退回上一个版本 | `make rollback`，目标 < 5 分钟 |
| 全链路追踪 / Trace | 一次提问经过了哪些步骤、每步耗时多少 | Langfuse |
| SSE | 一种让答案一个字一个字出现的网页技术 | V1 流式输出（比 WebSocket 更简单，优先选它） |
| WebSocket | 双向长连接，"打电话"式的通信 | **降级备选**：企业代理常拦 WS，V1 用 SSE 为主 |

## 五、业务术语（本项目特有）

| 术语 | 我的意思 | AI 容易误解成什么 | 在系统里怎么处理 |
|------|---------|-----------------|----------------|
| 知识库 | 一个逻辑文档集合（如"制度库""产品库"） | 理解成数据库实例 | 一个知识库对应一组文档 + 一套 RAG 策略 |
| 密级 | 文档的机密等级：公开 / 内部 / 部门专属 | 理解成文件加密 | 作为 chunk 的元数据，参与**检索前的权限过滤** |
| 部门专属 | 只有指定部门的人能看 | 理解成"文档作者所属部门" | 是"授权给谁"，与"谁上传的"无关 |
| 越权 | 用户看到了他无权访问的内容 | 理解成"登录失败" | 指检索结果里出现了越权 chunk，是数据泄露事故 |
| BadCase | 答错/答偏/答不出的真实案例 | 理解成"报错" | 专指质量问题，必须归档进评估集 |
| 缺口 | 用户问了但知识库里没有答案 | 理解成系统缺陷 | 它是**知识库建设**的输入，不是 bug |

## 六、评估平台术语（V1）

| 术语 | 大白话 | 类比 | 在本项目里指什么 |
|------|-------|------|----------------|
| **评估集 / Golden Set** | 一套"题目 + 标准答案"，用来给系统打分 | 考试的试卷 | `evals/golden_set.yaml`；V0.1 30 条 → V1 100+ 条 |
| **标准答案确认** | 由人（我）逐条判断"这个答案对不对""这题该不该拒答" | 老师批改卷子 | **未经确认的题目不得进入 `active` 数据集**（数据库约束兜底） |
| **基线 / Baseline** | 优化之前的那一次评估结果 | 出厂原始参数 | 没有基线，你无法证明优化有效，也无法证明没把别处改坏 |
| **回归对比** | 两次评估**逐条**对比，找出变好 / 变差的题 | 两份体检报告逐项对照 | `GET /eval/runs/{id}/items?changed_only=true` |
| **检索指标**（Recall@K / MRR） | "找资料"这一步做得怎么样 | 图书馆找书找得准不准 | 只评检索，不涉及生成 |
| **生成指标**（忠实度 / 相关性 / 引用准确率） | 答案本身写得好不好 | 答题有没有跑题、有没有抄错 | 忠实度直接衡量幻觉率 |
| **RAGAS** | 一套自动算 RAG 质量分数的开源工具库 | — | 只借用它的**指标定义**；平台不引入 |
| **对照实验法** | 同一题分别"只跑检索"和"跑完整链路"，看哪一步坏了 | 电路分段测电压 | 归因的**判定依据**，准确率接近 100%，单条几厘钱 |
| **归因候选 / 归因结论** | 见第七节易混淆对照 | — | — |
| **BadCase** | 确认过的真实质量问题案例 | 病历 | 与用户反馈（候选）分表存储 |
| **回灌 / Promote** | 把线上失败变成评估集里的一道题 | — | 只产出**候选**，合入必须人工确认 |
| **评估口径 / 线上口径** | 见第七节易混淆对照 | — | — |
| **SQL 通道的评估术语**（V2） | 见第三节（路由准确率 / 执行准确率 EX / 结果集比对） | — | — |

> **这一节存在的意义**：需求里那句"自动识别 BadCase 并给出优化方向"，
> 如果只看字面，你会以为要建一个分类器。
> 看完这张表你会知道：**它在本项目里被拆成了"对照实验法 + 候选归类 + 人工确认"三件事**，
> 每一件都有明确的输入输出和成本。

> **（V2）两个通道的评估指标禁止相加或平均**（`metrics.doc.*` vs `metrics.sql.*`）。
> 题目数不同、难度不同、分母不同，加权口径没有意义。
> 报告里**各出一张表，不出现合计行**——理由见 `evals/README.md` 第十节。

## 七、易混淆对照（AI 混淆会导致严重逻辑错误）

| 词 A | 词 B | 区别 |
|------|------|------|
| 检索失败 | 生成失败 | 前者是"没找到资料"，后者是"找到了但没用/编造"。**定位问题时必须分开统计** |
| 拒答 | 报错 | 拒答是正确行为（返回 200 + refused=true）；报错是故障（返回 5xx） |
| 权限过滤 | 权限校验 | 过滤是"检索时只取有权的"（在 SQL 里做）；校验是"操作前判断能不能做" |
| 操作日志 | 审计日志 | 操作日志给我自己排错用，可清理；审计日志给合规看，**只追加、不可修改、有留存期** |
| 语料更新 | 索引更新 | 语料是原文，索引是向量/全文索引；改了语料**必须**重建索引，否则搜的还是旧的 |
| 缓存 | 记忆 | 缓存是性能优化（可删）；多轮对话的"记忆"是功能（V0.1 不做） |
| 分块大小 | 上下文长度 | 分块大小是"每块多少字"；上下文长度是"一次喂给模型的总量" |
| **Recall@K** | **context_recall（RAGAS）** | **必须分清，两者都叫"召回"但完全不同**：<br>`Recall@K` = 标准来源**是否出现在** Top-K 检索结果里（**检索层**，程序判定，与生成无关）；<br>`context_recall` = 生成答案**所依据的**上下文覆盖了标准答案的哪些事实点（**生成层**，必须模型判定）。<br>**同一个失败案例，前者可能 1.0、后者可能 0.4**。同时展示时必须标明看哪个、为什么 |
| **评估口径** | **线上口径** | 评估口径 = 离线单条、无缓存命中（`eval_runs.metrics.latency_eval` / `cost_eval`）；<br>线上口径 = 含缓存命中后的真实平均（来自 `query_logs`）。<br>**两者能差 2—3 倍，禁止相加或平均** |
| **归因候选** | **归因结论** | 候选是机器按规则产出的**分组**（`attribution_candidate`，允许大量 `unclassified`）；<br>结论是人确认的**判断**（`attribution_confirmed`，必须带判定依据）。<br>**只有结论才计入统计**。混为一谈会让你去修一个没坏的地方 |
| **feedback** | **badcase** | feedback 是"用户点了 👎"（**候选**，含误报）；badcase 是"确认过确实是问题"（**结论**，含归因与依据）。<br>两者必须分表，否则你的问题统计里会混进一半情绪化反馈 |
| **数据集（dataset）** | **评估集内容（items）** | 数据集是**元数据**（表里存）：名称、版本、checksum、四类分布；<br>题目本体是**文件**（Git + MinIO）。改题改文件，不调接口 —— 为了保留逐行 diff |
| **基线（baseline）** | **对比运行** | 基线是被**标记为基准**的那次运行（同一数据集下只允许一个）；<br>对比运行是"我这次要跟它比"的那次。**`config_snapshot` 不同的两次运行不可归因** |
| **缺口（gap）** | **答错（badcase）** | 缺口是"库里本来就没有"（要**补文档**）；答错是"库里有但没答对"（要**改代码**）。<br>混在一起，你的待办清单永远理不清 |
| **路由准确率**（V2） | **执行准确率 EX**（V2） | 路由准确率 = "该走哪条通道"判对了没（**静默失败**的源头）；<br>执行准确率 = "走对了通道之后，结果对不对"。<br>**路由错时，执行准确率再高也没用**——一个错误的答案执行得再完美，也是错的 |
| **语义层**（V2） | **提示词**（V2） | 语义层告诉模型"**世界上有哪些东西可以查、怎么算**"（YAML，人写的）；<br>提示词告诉模型"**该怎么把话翻成 SQL**"（md，人写的）。<br>**模型报"字段不存在"时改语义层，不要改提示词**——提示词改不出一个不存在的字段 |
| **校验未通过**（V2） | **拒答**（V2） | 校验未通过 = SQL 在**执行前**被闸门拦下（`unsafe_sql`，可能是攻击，也可能是语义层没覆盖）；<br>拒答 = 校验通过、但没有可靠的答案可给（`doc_no_match` / `scope_denied`）。<br>两者都返回 200，但**一个的修法是改白名单，另一个的修法是补内容** |
| **明细行**（V2） | **聚合数**（V2） | 明细行可以逐行做脱敏（正则有效）；**聚合数不能**（`sum(salary)` 是个合法数字，看不出敏感）。<br>所以 SQL 通道的敏感保护必须在**对象白名单**层做，不能靠输出脱敏 |
