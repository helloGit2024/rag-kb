# SQL 通道评估说明（evals/sql/README.md）· V2

> 这是 Text-to-SQL 通道的评估说明，与文档通道的 `evals/README.md` **并列**。
> 两者共用"标准答案必须人确认""版本上下文必须记录"这两条铁律，
> 但**指标、比对方式、数据集形态全部不同**。
>
> **最重要的一条纪律：两个通道的指标必须分区报告，禁止相加或平均。**
> 它们衡量的是完全不同的东西（"找资料找得准不准" vs "SQL 写不写得对"），
> 算出一个平均数只会得到一个没有意义的数字。

---

## 一、为什么不能复用文档通道的评估方式

| 维度 | 文档通道 | SQL 通道 |
|------|---------|---------|
| 判定对象 | 一段自然语言答案 | 一个结果集 |
| 判定方式 | 裁判模型打分（有主观性） | **逐值比对**（客观、可程序判定） |
| 数据前提 | 文档已入库 | **数据必须固定**（否则结果不可复现） |
| 相对时间 | 不涉及 | "上个月"依赖"今天" → **必须冻结** |
| 核心风险 | 幻觉、召回不足 | **路由错**（比生成错严重得多） |

> 其中"数据必须固定"和"必须冻结今天"是文档通道里根本不存在的两个约束，
> 也恰好是最容易漏掉、漏掉之后成绩完全不可信的两个。

## 二、指标（四条，互相不可替代）

| 指标 | 定义 | 及格线 | 谁判定 |
|------|------|-------|--------|
| ★ **路由准确率** | `expected_channel` 与 `actual_channel` 一致的比例 | ≥ 0.90 | 程序 |
| ★ **执行准确率 EX** | 生成 SQL 与标准 SQL 的**结果集是否一致** | ≥ 0.80，且相对基线下降 ≤ 2% | 程序 |
| SQL 侧**拒答正确率** | 该拒的题（字段/指标不存在、敏感列、越权、超能力）是否都拒答 | ≥ 0.95 | 程序 |
| SQL 侧**误拒率** | 该答的题被拒的比例 | ≤ 0.05 | 程序 |

**为什么"路由准确率"排在第一位**

写错 SQL 会报错或返回 0 行 —— **可见失败**，成本很低；
路由错会给出一个"语法完美、执行成功、数字真实存在、但答的不是用户问的问题"的答案
—— **静默失败，无人能发现**（详见 `docs/text-to-sql.md` 第一节）。

所以：**先修路由，再修生成。** 顺序反了会白花很多时间。

**为什么拒答正确率与误拒率必须成对**

只看"拒答正确率"可以把阈值拉到最严（什么都拒，得分 1.0）。
只看"误拒率"可以把阈值放到最松（什么都答，得分 0.0）。
两个一起看，才无法作弊 —— 与文档通道的 `refused_precision` / `over_refusal` 同源。

**为什么 `Precision@K` 在这里没有对应物**

文档通道的 `Precision@K` 是"陷阱指标"；SQL 通道干脆不设对应指标。
SQL 只有一个结果集，要么对要么错，中间没有"部分相关"这个概念。

## 三、★ 比结果集，不比 SQL 文本

**这是本文件里最容易做错的一条。**

| 做法 | 问题 |
|------|------|
| ❌ SQL 文本相似度 / 字符串匹配 | 两条完全不同的 SQL 可能结果一致（都是对的）；一条只差一个条件的 SQL 文本相似度很高但少算一半。**文本相似度与正确性无关** |
| ✅ **结果集逐值比对** | 标准 SQL 跑一遍、生成 SQL 跑一遍，比对两个结果集 |

**比对规则（必须逐条实现，不能"差不多就行"）**

| 规则 | 说明 | 为什么 |
|------|------|--------|
| **列序无关** | 只比对列**值集合**，不比列顺序 | `SELECT a, b` 与 `SELECT b, a` 结果等价 |
| **行序无关** | 除 `result_order_matters: true` 外，按多重集比对 | 题面没要求排序时，"有没有写 ORDER BY"不该成为判分因素 |
| **列名不参与比对** | 别名叫 `total` 还是 `sum` 不影响正确性 | 别名是表达习惯，不是正确性 |
| **数值容差** | 相对容差 `1e-6` | 避免 `AVG` 浮点精度差异造成误判 |
| **行数上限** | 标准答案行数 > `max_rows` 时，只比对截断后的部分并标注 | 与执行层一致 |
| **类型宽松** | `25000` 与 `25000.00` 视为相等；`"E015"` 与 `E015` 视为相等 | 不要因为类型差异判错 |

> **行序那一条要特别注意**：只有题面里出现"排序/排名/Top"时才校验顺序。
> 否则你会开始"教模型写 ORDER BY" —— 而用户并不关心顺序，
> 这属于把判分标准变成了风格偏好。

## 四、★ 固定数据集：否则"今天 100 分、明天 60 分"

结果集比对的前提是**数据不变**。业务库是活的，所以不能对着生产库跑评估。

```
evals/sql/
├── golden_set_sql.yaml     题目 + 标准 SQL + 标准结果 + 口径说明（走 Git）
├── seed.sql                ★ 固定种子数据（评估时灌入临时库）
├── expected/               标准结果的独立副本（防止标准 SQL 本身写错）
└── README.md               本文件
```

**跑评估的流程**

```
1. 建临时库（或用 docker 起的独立库）
2. 灌 evals/sql/seed.sql
3. 冻结"今天" = golden_set_sql.yaml → meta.frozen_now
4. 跑全量题目（逐条：路由 → 生成 → 校验 → 执行）
5. 比对结果集（按第三节规则）
6. 落 eval_runs（channel=sql）+ eval_run_items
7. 销毁临时库
```

**`frozen_now` 是一个容易被忽略但必须有的字段**

"上个月培训支出是多少"这句话，**换个日期就是另一道题**。
不冻结"今天"，这份题库会随时间自然腐烂：
下个月再跑，"上个月"变成了 10 月，而标准答案还写着 9 月的数字 ——
于是你会看到"准确率突然掉到 30%"，然后花一天去查模型哪里变了。

**`expected/` 与 `gold_sql` 的关系：它们不是冗余**

- `gold_sql` 是"怎么算出来的"，供人读、供排查；
- `expected/*.json` 是"算出来应该等于多少"，**由人工照 `seed.sql` 核算确认**。

**关键：标准答案不能由 `gold_sql` 跑一遍生成。**
那样等于用一个可能是错的 SQL 去验证另一个 SQL。
正确做法是**人工核算**（如 S001 的 `basis` 写的"逐条加：12000+8000+5000…"）。
`expected/` 的存在，就是为了让这种人工核算有一个可对比的落点。

## 五、归因：四种错，改的地方完全不同

沿用 `evals/attribution.md` 的"候选 + 人工确认"纪律，但候选规则不同：

| 错误类型 | 判定依据（程序可查） | 该改哪里 |
|---------|-------------------|---------|
| **路由错** | `actual_channel ≠ expected_channel` | 路由规则/阈值，**不是** SQL 生成提示词 |
| **语义层缺** | `reject_reason = unknown_object` | **补语义层**（加字段/加指标） |
| **口径错** | 执行成功、结果集不一致，但表/字段都对 | `metrics` 的 `time_column` / 过滤条件 / `scope_mode` |
| **权限错** | `scope_mode=own` 的答案没标注范围，或出现了越权行 | 权限映射（`scope_key` → 业务表权限列） |
| **生成错** | 执行成功、结果集不一致、且表/字段都对、口径也对 | 生成提示词 |

> **"语义层缺"最常被误判成"生成错"。**
> 你看到模型生成了个不存在的字段，第一反应是"模型不行"，
> 但真实原因往往是**语义层里没声明这个字段**。
> **先看 `nl2sql_logs.reject_reason` 再下结论** —— `unknown_object` 占比高
> 说明你在跟一个文档问题较劲，而不是模型问题。

**一个可运营的指标：`unknown_object` 排行**

把被拒的 `unknown_object` 按对象名聚合，就是一份"语义层该补什么"的待办清单。
**按排行按需补，不要一次把整库搬进语义层。**

## 六、与文档通道的关系（三条边界）

| # | 边界 | 为什么 |
|---|------|--------|
| 1 | **指标分区报告**，不混算 | 衡量的对象不同，平均无意义 |
| 2 | **文档通道的指标要陪着看** | 路由错会把本该走文档的题引到 SQL 上，那部分损失**记在文档通道的账上**（H7—H9 应保持一致） |
| 3 | **题库存两个文件，不合并** | `evals/golden_set.yaml`（doc）+ `evals/sql/golden_set_sql.yaml`（sql）；数据集元数据的 `channel` 字段区分（见 `docs/openapi.yaml` → `EvalDataset.channel`） |

## 八、为什么题库里必须有 `route_to_doc` 题（最后一件事）

如果题库里全是 SQL 题，那么**"所有问题都走 SQL"也能拿满分** ——
而路由错误恰恰是这个功能最大的风险。

所以：**`route_to_doc` 这一组的存在意义，不是提高覆盖率，而是让路由这条门禁有效。**
同理，`permission` 这一组的存在意义是让"聚合范围标注"这条门禁有效（AC-30）。

**没有反问句的题库，测不出判断题。**
