# expected/ —— 标准结果的人工核算副本

> 每个文件对应 `golden_set_sql.yaml` 里一道 **`expected_channel: sql`** 的题。
> 文件名即题号：`S001.json`、`S007.json`……

## 为什么要有这个目录（和 `gold_sql` 不是冗余）

| 文件 | 回答的问题 | 谁产出 |
|------|-----------|-------|
| `golden_set_sql.yaml` → `gold_sql` | **怎么算**（SQL 本身） | AI 起草，你确认表/字段/口径 |
| `expected/*.json` → `result` | **算出来应该等于多少** | **你人工核算**（照 `seed.sql` 加/数） |

**关键：`result` 不能由 `gold_sql` 跑一遍生成。**
那样等于用一个可能是错的 SQL 去验证另一个 SQL —— 两个错误会互相印证。
正确做法是人工核算，把过程写进 `basis`（如 S001 的"12000+8000+5000…"）。

**这个目录的价值有两层**：
1. **它拦得住"标准 SQL 写错"这一类错误** —— 人工算出的数字和 SQL 跑出的数字对不上时，
   你会立刻知道是 SQL 写错了，而不是系统答错了；
2. **它让"口径"变成可讨论的东西** —— `wrong_answers_that_look_right` 这一栏
   列出的是"其他口径算出来的数字"。**这些数字都是能跑出来的，也都看起来合理。**
   把它们的值写明，你才能在评审时回答"为什么不是 60500"。

## 文件格式

```jsonc
{
  "id": "S001",
  "question": "…",                       // 与题库一致，便于人工对照
  "expected_channel": "sql",
  "scope_mode_used": "own",              // own | global
  "must_label_scope": true,              // 答案里必须出现聚合范围标注
  "result_order_matters": false,         // 仅题面要求排序时为 true
  "columns": ["total", "cnt"],           // 仅用于人工阅读，不参与比对
  "result": [ [62500.00, 7] ],           // ★ 参与比对的值（列序/行序无关）
  "basis": ["…逐条核算过程…"],            // ★ 人工核算依据
  "excluded": ["…被排除的行及原因…"],      // 便于事后复核
  "wrong_answers_that_look_right": {     // ★ 其他口径会得到的数字
    "60500.00": "按 submit_date 归属月份",
    "66000.00": "未过滤 status",
    "72500.00": "时间范围覆盖了 2025-09"
  }
}
```

## 只放 `sql` 类的题

**`refuse` / `route_to_doc` / `permission`（部分）类不放这里** —— 它们的判定是
"有没有拒答 / 走了哪个通道 / 有没有标注范围"，不是结果集比对，
所以它们的期望值直接写在题库条目里（`reject_reason`、`must_label_scope`）。

**`permission` 类里 `expected_channel: sql` 的题要放**（如 S016、S017）——
它们**同时也是结果集比对题**，只是第二个判定条件是"答案有没有标注范围"。
两道判定都要过。

## 当前样本

|------|------------|
