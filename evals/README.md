# 评估说明（evals/README.md）

> 这份文件回答三个问题：**衡量什么、多少算及格、怎么跑。**
>
> **最重要的一条认知**：大模型的输出是概率性的。
> 你改了一句提示词、调了分块大小、换了模型——**你无法靠"试几个问题感觉一下"
> 判断是变好了还是变差了。**
>
> 有评估集，优化是工程；没有评估集，优化是玄学。
>
> **版本范围**：本文件写的是**文档通道**的评估（V0.1 起）。
> V2 的 Text-to-SQL 通道是**另一套指标、另一套数据集、另一种比对方式**，
> 见 `evals/sql/README.md`。两条通道的指标**必须分区报告，禁止相加或平均**。

## 一、为什么"传统测试"不够用

| | 传统测试 | RAG 系统 |
|--|---------|---------|
| 输出 | 确定性（输入 A 必得 B） | 概率性（同一问题，两次答案措辞不同） |
| 判断 | 字符串相等 | 需要语义判断 |
| 改动的可预测性 | 高 | **低——改动 A 经常让 B 变差** |

所以必须有：**一套固定的题目 + 一套自动评分标准 + 一条及格线。**

## 二、评估指标（三层）

### 第 1 层：检索质量（只评"找资料"这一步）

| 指标 | 衡量什么 | 及格线 | 不达标时用户会看到什么 |
|------|---------|-------|-------------------|
| **Recall@5** | 前 5 条里有没有标准来源 | ≥ 0.85 | 库里明明有，就是搜不出来 |
| **MRR** | 正确答案排在第几位 | ≥ 0.70 | 答案对但引用的资料不相关 |
| 上下文精确度 | 检索到的内容有多少是无关的 | ≥ 0.70 | 答案里混进不相关内容，甚至答偏 |

**为什么要单独测检索**：端到端出问题时，你需要知道是"没找到资料"
还是"找到了但没用"。不拆开，你只能猜。**而这两类的修法完全不同。**

### 第 2 层：生成质量（前提是资料已给对）

| 指标 | 衡量什么 | 及格线 | 不达标时用户会看到什么 |
|------|---------|-------|-------------------|
| **忠实度 Faithfulness** | 答案是否完全来自给定资料 | ≥ 0.85 | 答案很流畅但内容是编的 |
| 答案相关性 | 是否回答了用户真正问的问题 | ≥ 0.80 | 答非所问，绕圈子 |
| 引用准确率 | 引用的原文是否真的支持该结论 | ≥ 0.90 | 点开引用发现原文和结论对不上 |

> **忠实度是最关键的指标**——它直接衡量幻觉率。

### 第 3 层：端到端体验

| 指标 | 衡量什么 | 及格线 |
|------|---------|-------|
| 任务完成率 | 用户是否拿到可用答案 | ≥ 0.90 |
| **拒答正确率** | 应拒答的题目里真的拒答了的比例 | ≥ 0.90 |
| **误拒率** | 不该拒答的题目里被拒答的比例 | ≤ 0.05 |
| P95 延迟 | 95% 的请求在多少秒内返回 | < 5 秒 |
| 单次成本 | 每次问答平均花费 | < ¥0.03 |

## 三、"应拒答"类怎么评分（重点）

- **拒答正确**：系统明确说明未找到相关信息（恰好等于固定句式），且未生成任何知识库外内容。
- **误拒**：知识库里确实有答案，但系统说找不到。

### 为什么必须同时设"拒答正确率"和"误拒率"？

因为**任何单一指标都可以被作弊式优化**。

- 如果只考核"拒答正确率"，最省力的做法是把阈值调到极严——
  系统对所有问题都说"我不知道"。拒答正确率 100%，但系统完全没用。
- 如果只考核"任务完成率"，最省力的做法是永远不拒答、什么都敢答。
  完成率很高，但幻觉率爆炸。

**所以这两个指标必须成对存在、互相制约。**

> **通用原则**：设计指标体系时，任何你打算优化的指标，都要问一句
> "如果只优化这一个，系统会往哪个极端跑？"然后设置一个反向指标把它拉回来。
> 同类例子：召回率与精确率、覆盖率与成本、回答速度与回答质量。

## 四、怎么跑评估

| 命令 | 干什么 | 大概耗时 / 花费 |
|------|-------|---------------|
| `make eval` | 跑完整三层评估，结果**同时写入 `eval_runs` + `eval_run_items`** | 约 6 分钟（30 条 × 检索+生成+裁判） |
| `make eval-lint` | 校验评估集文件：id 唯一、类别在枚举内、refuse 题的 `should_refuse` 必须为 true | 秒级 |
| `make eval-compare` | 与基线逐项对比。**先校验 checksum**，不一致直接拒绝跑 | 秒级 |
| `make eval-attribute` | ★ **只跑检索路径**，回填 `retrieval_hit` 与归因候选 | 30 条 < 2 分钟，< ¥0.2 |
| `make eval-report` | 生成归因汇总（**只统计人工已确认的结论**，显式显示"未确认 N 条"） | 秒级 |

| 项目 | 内容 |
|------|------|
| 跑了多少条 | 30 条（V0.1）→ 100+ 条（V1） |
| 结果存在哪 | **数据库 `eval_runs`（汇总）+ `eval_run_items`（逐条）**；报告文件另存 `evals/report/YYYY-MM-DD.json` |
| 失败案例 | `evals/failures/YYYY-MM-DD.md`，并逐条进 `eval_run_items` |
| 数据集版本 | 元数据在 `eval_datasets`；题目本体在 `evals/golden_set.yaml`（Git） |

> **为什么结果要入库，不能只留 JSON 文件**：
> 只留文件，"这次是跟哪个基线比"这个问题就没有答案 ——
> 它会只存在于你的记忆里，然后你在第 4、5 次评估时开始怀疑一切。
> 决策与代价见 `docs/adr/0008`。

## 五、自动评分怎么做（LLM-as-Judge）

用一个模型给答案打分，而不是用代码比对字符串。**完整提示词见 `evals/judge-prompt.md`。**

### 必须遵守的四条

1. **裁判模型不能和被测模型是同一个。**
   否则它会系统性地偏袒自己（"我也会这么答，所以是对的"）。
   建议裁判用比线上高一档的模型。

2. **必须逐维度打分 + 给出理由，不要只给总分。**
   只给总分你无法定位问题——你知道"这次 78 分"，但不知道为什么掉了 5 分。

3. **必须定期人工抽检校准。**
   每轮评估抽 20—30 条人工复核。
   **如果裁判和我的判断偏差超过 15%，说明裁判不可信，需要重写评分标准。**

4. **评分标准要写得非常具体。**
   - 差（会得到随机分数）："答案质量好不好？"
   - 好："答案中的每一个事实性陈述，都能在给定资料原文中找到依据。
     有任一处找不到依据，标记为不忠实。"

### 哪些题必须人工评分，不能交给模型裁判

- **涉及精确数字的题（金额、日期、数量）** —— 裁判容易忽略细微的数字错误
- **涉及权限判断的题** —— 是否越权必须人工确认
- **我自己也拿不准标准答案的题** —— 先别放进评估集
- 主观性强的问题（"这个回答是否礼貌得体"）—— 不适合自动评分

## 六、归因（详见 `evals/attribution.md`）

指标掉了，**改哪里**？这是评估跑完之后真正的问题。

本项目**不做自动分类器**，用**对照实验法**：同一题分别"只跑检索"和"跑完整链路"，
依据 `retrieval_hit` 这个**布尔值**判断是检索的锅还是生成的锅。
准确率接近 100%，单条成本几厘钱。

| 概念 | 谁产生 | 是否可以自动 |
|------|-------|------------|
| `attribution_candidate` 归因**候选** | 规则脚本 | ✅ 可以（允许大量 `unclassified`） |
| `attribution_confirmed` 归因**结论** | **人（我）** | ❌ 绝对不行，且必须同时留判定依据 |

**只有结论计入统计。** 报告里必须显式显示"未确认 N 条"。

> 完整方法（判定表、候选规则、确认纪律、确认后该改哪）见 **`evals/attribution.md`**。
> 决策背景与代价见 `docs/adr/0008`。

## 七、评估口径 vs 线上口径（两个数字不可混用）

同一件事有两套数字，**差 2—3 倍**，混在一起会让你对预算和性能的判断偏差一倍。

| | 评估口径 | 线上口径 |
|--|---------|---------|
| 来源 | `eval_runs.metrics.latency_eval` / `cost_eval` | `query_logs` 聚合 |
| 场景 | 离线单条，**无缓存命中** | 真实流量，**含缓存命中** |
| 平均值典型差异 | 单次 ¥0.021 | 含缓存后可能 ¥0.008 |
| 用途 | 比较两次改动的优劣（**同口径才可比**） | 判断这个月花了多少钱、真实 P95 是多少 |

**两条纪律**

1. 报告里每个指标旁必须标明它属于哪个口径；
2. **禁止**把两个口径的数字相加或求平均。

> 顺带一个容易混的：**`Recall@5` 与 RAGAS 的 `context_recall` 不是同一个指标**。
> 前者衡量"标准来源在不在 Top-5 里"（检索层，程序判定）；
> 后者衡量"答案所依据的上下文覆盖了标准答案的哪些事实点"（生成层，模型判定）。
> **同一个失败案例，前者可能是 1.0、后者可能是 0.4。**
> 同时展示时必须标明看哪个、为什么（见 `docs/glossary.md` 第七节）。

## 八、评估集的维护规则

### 什么时候加题

- **线上发现答错时（最重要）→ 立刻把这个真实失败案例加进来**
- 新增了功能或改了检索策略时
- 发现某类问题完全没有覆盖时

> **"失败案例驱动"是让评估集保持真实的关键。**
> 初始评估集往往是你拍脑袋想的问题，而真实用户问的问题经常超出你的想象。

**加题的三种来源**

| 来源 | 路径 | 是否需要人工确认 |
|------|------|----------------|
| 我想到一个问题 | 直接写进 `golden_set.yaml` | 标准答案仍需我确认 |
| 评估失败案例 | `eval_run_items` → 手动整理 | 是 |
| **线上真实失败** | `feedback` → 确认为 `badcases` → **promote** → `evals/pending/` → 我确认 → 合入 `golden_set.yaml` | **是，且不可跳过** |

> **promote 只生成"候选题目"，不会自动写进 `golden_set.yaml`。**
> 这条限制是刻意的：如果系统能自己往题库里加题，就等于自己出题、自己定答案，
> 评估立刻失去衡量能力。详见 `docs/adr/0008` 与 `spec.md` AC-25。

### 加题 / 改题 / 删题

| 操作 | 规则 |
|------|------|
| 加题 | 随时可以。优先加真实线上失败案例。 |
| 改题 | 必须说明理由。如果是因为改分块策略导致原文变了，需同时更新旧版本的对比基线。 |
| 删题 | **必须写理由，并且必须有人复核。** |

### 为什么"为了让评估通过而删题"是绝对禁止的

评估集是**唯一的客观标尺**。一旦标准可以为了通过而修改，
它就失去了衡量能力——**你不再是在优化系统，而是在优化那个数字。**

这就像为了考试成绩好而把考卷题目删掉：成绩确实变好了，但你什么都没学会。

**正确做法**：如果某道题一直过不了，先判断是"题目出错了"还是"系统真的不行"。
- 题目出错（标准答案本身有误、题目有歧义）→ 可以改，但要记录理由
- 系统真的不行 → **保留它，它正在告诉你真实存在的问题**

## 十、SQL 通道的评估（V2，只在本文件里留指针）

> **详细内容全部在 `evals/sql/README.md`**，这里只说明"为什么要分成两份文件"。

| 维度 | 本文档（文档通道） | `evals/sql/`（数据通道） |
|------|------------------|----------------------|
| 判定对象 | 一段自然语言答案 | 一个结果集 |
| 判定方式 | 裁判模型打分（有主观性） | **逐值比对**（客观、可程序判定） |
| 是否需要固定数据 | 不需要 | **必须**（`seed.sql` → 临时库 → 跑完销毁） |
| 是否依赖"今天" | 不依赖 | **依赖**（"上个月"要靠 `frozen_now` 冻结） |
| 核心指标 | Recall@K / 忠实度 / 拒答率 | **路由准确率 / 执行准确率 EX** / SQL 侧拒答率 |
| 最大风险 | 幻觉、召回不足 | **路由错**（比生成错严重得多） |

**三条不可违反的边界**

1. **指标分区报告。** `metrics.doc.*` 与 `metrics.sql.*` 分开返回（见 `docs/openapi.yaml` → `EvalRun.metrics`）。**禁止相加或平均** —— 它们衡量的东西不同，平均出来的数没有意义。
2. **文档通道的指标要陪着看。** 路由错会把本该走文档的题引到 SQL 上，那部分损失**记在文档通道的账上**（H7—H9 应保持一致）。所以启用 SQL 通道后**不能只看 SQL 的指标**。
3. **题库存两个文件。** `evals/golden_set.yaml`（doc）与 `evals/sql/golden_set_sql.yaml`（sql）不合并；数据集元数据用 `channel` 字段区分（见 `docs/openapi.yaml` → `EvalDataset.channel`）。

**为什么不能"合成一份评估说明就完事"**

因为两者的**坑完全不同**：文档通道的坑是"裁判模型自身有偏差"，
SQL 通道的坑是"数据变了 / 日期没冻结 / 比错了对象（比 SQL 文本而不是比结果集）"。
写在一起，你最可能漏掉的恰恰是"数据必须固定"这条 ——
而漏掉它，成绩会**悄悄**变成不可信（不像裁判偏差那样能从数字上看出异常）。
