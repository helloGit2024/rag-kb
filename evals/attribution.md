# 归因手册（evals/attribution.md）

> 这份文件只回答一个问题：**评估跑完，指标掉了，接下来改哪里？**
>
> 结论先行：**不要指望自动分类器告诉你原因。**
> 用一次"对照实验"就能把准确率做到接近 100%，而成本是几厘钱。
> 决策依据与代价见 `docs/adr/0008`。

---

## 一、为什么"自动分类"不可靠

失败类型在自动指标上是**耦合**的。举两个真实例子：

| 现象 | 是召回失败吗？ | 是生成失败吗？ |
|------|--------------|--------------|
| 问"年假多少天"，答了"病假 10 天" | 可能（没搜到年假条款） | 也可能（搜到了年假条款，但答错内容） |
| 问"报销时限"，答"一个月内"（实际 60 天） | 可能（搜到的是旧版制度） | 也可能（搜到了正确条款，但模型换了说法） |

只看"答案相关性低 + 忠实度低"这个组合，**两种原因都符合**。

所以按需求文档写的"自动识别 BadCase 并给出优化方向"直接实现，
你会得到一个准确率 60—75% 的分组，然后**基于它去调参数**——
结果是把时间花在修一个根本没坏的地方。

> 这不是"AI 不够强"的问题，是**信息不足**的问题：
> 单看最终答案，无论谁来判，都缺少"检索这一步到底给了什么"这个信息。

## 二、对照实验法（本项目采用）

对每个失败案例，跑**两个**链路：

| 路径 | 跑什么 | 看什么 | 单条成本 |
|------|-------|-------|---------|
| **A. 只检索** | query → 检索 → 取 Top-5 | **标准来源是否出现在 Top-5 里**（写入 `retrieval_hit`） | ≈ ¥0.0002（本地嵌入）/ ≈ ¥0.002（云端嵌入） |
| **B. 完整链路** | query → 检索 → 生成 → 引用回绑 | 答案、引用、忠实度 | 正常问答成本 |

**判定表（`retrieval_hit` 是布尔值，所以判定没有猜测成分）**

| retrieval_hit | 生成结果 | 结论 | 该改哪 |
|---------------|---------|------|-------|
| ✅ 命中 | 答对 | 正常 | — |
| ✅ 命中 | 答错 / 编造 | **生成问题** `generation` | 提示词（强制逐句依据 + 引用编号由程序注入）、引用回绑、裁判标准 |
| ✅ 命中 | 却拒答了 | **过度拒答** `generation` | 拒答判定阈值（同时看误拒率） |
| ❌ 未命中 | 拒答 | 库里**有** → **检索问题** `retrieval`<br>库里**没有** → **数据缺口** `data_gap` | 分块 / 加 BM25 / 重排 / 查询改写<br>vs 补文档 |
| ❌ 未命中 | 硬答 | **双重问题**：`retrieval` + 幻觉 | 先修检索，再看生成 |
| — | 出现无权内容 | `permission` | **停下来，先修权限**，其他事都往后排 |

> **为什么这个判定是确定的**：A 路径把"检索"单独拎出来看了，
> 它的输出是"命中 / 没命中"，不是"像不像命中"。
> 判定链上没有任何一个需要模型打分的环节。

**一轮 30 条题的总成本**：A 路径不到 2 毛钱（30 × ¥0.002 ≈ ¥0.06，本地嵌入更低）。

## 三、候选归因的产生规则（机器做，只到"候选"为止）

下面这几条可以由脚本无脑执行，产出 `attribution_candidate`。
**它们不产生结论，只产生分组。**

| 条件 | 候选值 | 说明 |
|------|-------|------|
| `refused=true` 且 `retrieval_hit=true` | `generation_suspect` | 资料在手却没答 → 疑似拒答阈值太严 |
| `refused=false` 且 `retrieval_hit=false` 且 `faithfulness < 0.85` | `retrieval_suspect` | 没找到资料却硬答 → 疑似召回失败叠加幻觉 |
| `refused=false` 且 `retrieval_hit=true` 且（`off_topic` 或 `wrong_number`） | `generation_suspect` | 资料在手却答偏/答错数字 |
| `status=error` | `unclassified` | **先看工程错误，不参与质量归因** |
| 其余 | `unclassified` | 允许大量存在，见下方说明 |

> **允许 `unclassified` 大量存在，是这份设计里最反直觉、也最重要的一条。**
> 强行给每条都贴一个原因，只会让你分不清哪些是真判断、哪些是兜底填充。
> **一个诚实的"未归类"，比一个编造的结论有价值得多。**

## 四、人工确认（不可省略的一步）

对每条候选，你只做两件事，**每条约 20—40 秒**：

1. 打开该条详情（题目、Top-5 检索结果、系统答案、引用）
2. 看 `retrieval_hit` 的值 → 点确认，或改成你判断的结论，并写一句依据

**两条纪律**

- **`attribution_confirmed` 为空的行不计入任何统计。**
  报告里必须显式显示"未确认 N 条"，而不是把它们悄悄算进某一类。
- **候选规则判错时，先记下来。** 同一类错判出现 **3 次以上**，
  说明候选规则要改 —— 而不是说明"该加自动分类器了"。

> 30 条题的人工确认约 15 分钟，100 条约 40 分钟。
> 这是这个项目里**投入产出比最高的 40 分钟**：它决定你下一周往哪个方向优化。

---

## 五、确认之后干什么（按性价比排序）

| 结论 | 第一优先动作 | **不要**做 |
|------|------------|----------|
| `retrieval` 召回失败 | 用 `docs/experiments/` 的方式做**单变量**对比：调 chunk 大小 / 加 BM25 / 加 rerank，一次只上一个 | 不要三个一起上，否则又是一次"无法归因" |
| `generation` 幻觉 | 收紧提示词（强制逐句依据、引用编号由程序注入），先看忠实度 | 不要先换更大的模型（检索差的时候换模型几乎没用） |
| `generation` 过度拒答 | 放宽拒答阈值，**同时看误拒率有没有变差** | 不要只盯拒答正确率 |
| `data_gap` 知识缺口 | 补文档；或明确归入"本就不该答"（`wontfix` + `data_gap_wontfix`） | 不要试图让模型"猜"出来 |
| `permission` 越权 | **停下手上的优化**，先修权限并补一条越权测试用例 | 不要留到"以后再说" |

## 六、一轮归因的完整流程（30 条约 40 分钟）

```bash
make eval              # 跑评估 → 写入 eval_runs + eval_run_items
make eval-attribute    # ★ 只跑检索路径，回填 retrieval_hit 与 attribution_candidate
#     → 打开 BadCase 面板（或看 evals/pending/ 下的清单），按候选分组逐条确认
make eval-report       # 生成归因汇总（只统计已确认的）
```

> `make eval-attribute` 只跑检索、不调生成模型，所以它**很便宜也很快**，
> 可以放心在每次改检索参数后都跑一遍。

## 七、两个经常被搞混的问题

**1. "指标掉了"不等于"需要归因"。**
先判断这是不是噪声。在 30 条题上，±3 个点是正常波动范围，
你无法区分"真的变差了"和"这次抽到的随机性不同"。
判定方法：**同一版本连跑两次**，看两次之间的波动有多大。
这正是评估集必须扩到 100 条以上的原因（30 条的波动可达 ±8%）。

**2. 归因是给"失败条目"做的，不是给"汇总指标"做的。**
汇总指标掉了，它只告诉你一件事：**去逐条看**。
汇总指标本身无法被归因 —— 对 0.891 这个数字问"为什么"是没有答案的。

## 八、与需求文档的差异（记录在此，避免以后重复讨论）

需求里写的是"自动识别 BadCase（召回失败、幻觉、答非所问），归类，
给出优化方向（分块调整 / topK 调参 / 换 rerank / query 优化）"。

本项目的实现是：
- **归类**：✅ 做，但只到**候选**，且允许大量 `unclassified`；
- **优化方向**：✅ 做，但形式是"你确认结论后，看第五节这张表"，
  而不是系统输出一段建议文字；
- **自动**：❌ 不做。人工确认环节是刻意保留的，不是没做完。

理由见 `docs/adr/0008` 第五节与第六节第 3 条（含什么条件下应该重新考虑）。

## 九、SQL 通道的归因（V2）

> 上面八节讲的是**文档通道**。SQL 通道（`docs/text-to-sql.md`）有一类失败是
> 文档通道里根本不会出现的：**答案语法完美、执行成功、数字真实、但答非所问**。
> 这一节把它的归因差异写清楚，否则你会继续用"检索失败 / 生成失败"这套框架去套，
> 然后得出一个错误的结论。

### 9.1 为什么 SQL 通道的归因不能复用第二节的对照实验

第二节的判定核心是 `retrieval_hit`（**标准来源是否出现在 Top-5**）——
它是一个布尔值，所以判定没有猜测成分。

SQL 通道没有"检索"这一步，取而代之的是**路由**与**语义层**两个环节。
所以对照实验要换成一个四步检查，每一步的输出都是**确定的**（不是"像不像"）：

| 步 | 跑什么 | 看什么 | 输出 |
|----|-------|-------|------|
| ① 路由 | 只跑路由（不生成 SQL） | `nl2sql_logs` 里的 `channel`、`route_confidence` | `doc` / `sql` / `hybrid` 三选一 + 置信度（数值，无猜测） |
| ② 语义层 | 拿模型的候选指标/字段名去查 `semantic_layer.yaml` | 是否命中 `metrics` / `tables` 的键 | `hit` / `unknown_object`（枚举，无猜测） |
| ③ 执行 | 用**人工写好的标准 SQL**跑一遍 | 返回的行与列 | 与 `expected/` 比对（结果集比对，见 9.2） |
| ④ 生成 | 用**模型生成的 SQL**跑一遍 | 返回的行与列 | 与 ③ 的结果比对 |

**④ 与 ③ 的差 = 生成问题；③ 与 `expected/` 的差 = 口径或权限问题。**
两步分开跑，才能把"模型 SQL 写错"和"语义层口径定义错"分开——
这两个的修法完全不同（一个改提示词，一个改 YAML）。

### 9.2 SQL 通道的五种错（判定依据与修改动作）

| 结论码 | 现象 | 判定依据（确定值） | 该改哪 |
|--------|------|------------------|-------|
| `route_wrong` | 该走文档的题走了 SQL（或反之） | ① 的 `channel` ≠ `expected_channel` | 路由规则 / 阈值（`docs/text-to-sql.md` 第五节）；**不要改提示词** |
| `semantic_gap` | 报 `unknown_object`，或字段"不存在" | ② 命中 `unknown_object` | **补 `semantic_layer.yaml`**（加 metric / 加 enum / 加 table）；**不要改提示词** |
| `metric_wrong` | 数字算错，但 SQL 能跑通 | ③ 与 `expected/` 不符，且 ④ 与 ③ **一致** | 改 `metrics` 的 `time_column` / `where` / `scope_mode` |
| `permission_wrong` | 越权给了数，或该标注范围却静默聚合 | `scope_snapshot` 与 `expected` 的权限范围不符；或答案缺"基于 N 条记录"标注 | 权限映射；或指标的 `scope_mode` 声明 |
| `generation_wrong` | SQL 语法错 / 引用了语义层里没有的对象 | ④ 与 ③ 不符（③ 是对的） | 提示词、few-shot；**这才是"模型问题"** |

> **`unknown_object` 排行是可运营指标，从空开始按需补语义层。**
> 语义层白名单**故意不预先写全**（见 `docs/text-to-sql.md` 第四节）——
> 空着的时候看起来"什么都查不了"，但这正是设计意图：
> **宁可拒答，也不让模型猜一个字段名。** 你每周看一次 `unknown_object` 排行，
> 按出现频次从高到低补语义层，三周后覆盖率自然够用。

### 9.3 最容易被误判的一类：把 `semantic_gap` 判成 `generation_wrong`

你看到模型生成了一个不存在的字段，第一反应是"模型不行"。
但真实原因往往是**语义层里没声明这个字段**——模型没有任何地方可以查，它只能猜。

**纪律：先看 `nl2sql_logs.reject_reason`，再下结论。**

- `reject_reason = unknown_object` 占比高 → 你在跟一个**文档问题**较劲（补 YAML），
  而不是模型问题（改提示词）——改提示词永远改不好一个不存在的字段。
- 只有在 ② 命中、③ 正确、④ 却跑错时，才动提示词。

> 这和第一节那句"失败类型在自动指标上是耦合的"是同一个道理，
> 只是这次耦合的两端变成了**语义层覆盖度**与**生成能力**。

### 9.4 两个通道的归因统计**禁止合并**

`metrics.doc.*` 与 `metrics.sql.*` 不能相加、不能平均，归因统计同理：

| 合并会怎样 | 后果 |
|-----------|------|
| 把 SQL 的 `route_wrong` 混进文档的 `retrieval` | 你会去"调分块大小"修一个路由问题，永远修不好 |
| 用文档的"拒答正确率"看 SQL 通道 | SQL 的拒答（`scope_denied` / `unknown_object`）性质完全不同，分母也不同 |
| 算一个"总体准确率" | 两个通道的题目数不同、难度不同，加权口径没有意义 |

**做法**：归因报告里两个通道**各出一张表**，表头一致，但**不出现合计行**。
这与 `evals/README.md` 第十节"为什么不能合成一份"是同一件事的两种说法。

### 9.5 一轮 SQL 通道归因的流程

```bash
make seed-sql          # 起临时库并灌入固定数据集（seed.sql + frozen_now）
make eval-sql          # 跑 golden_set_sql.yaml → 写入 eval_runs + eval_run_items
make eval-report       # 归因汇总（两个通道各一张表，不合并）
```

> **注意 `frozen_now`**：SQL 题库里带时间词的题（"上个月""最近 3 个月"）
> 依赖一个**冻结的"今天"**（`golden_set_sql.yaml` 的 `meta.frozen_now`）。
> 如果评估脚本用系统时间而不是 `frozen_now`，这些题会**随时间腐烂**——
> 今天 100% 通过，下个月全错，而你会以为是模型退化了。
> 归因时如果看到大量 `metric_wrong` 集中在这类题上，**先查 `frozen_now` 有没有被传进执行链路**。
