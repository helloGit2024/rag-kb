# 自动评分裁判提示词（evals/judge-prompt.md）

> 这份文件是**用来喂给裁判模型**的提示词模板，不是给人读的说明。
> 说明见 `evals/README.md` 第五节。
>
> 使用方式（`evals/run_eval.py` 中的调用逻辑）：
> 1. 从 `golden_set.yaml` 取一条题
> 2. 把 `{{question}}` / `{{expected_answer}}` / `{{expected_sources}}` 填进去
> 3. 把系统实际检索到的资料填入 `{{retrieved_context}}`
> 4. 把系统实际生成的答案填入 `{{actual_answer}}`
> 5. 用**与线上不同的、更强一档的模型**调用本提示词
> 6. 解析返回的 JSON，累加各项分数

---

## 一、裁判提示词本体（system prompt）

```markdown
你是一名严格的 RAG 系统答案质量评审员。你的唯一任务是**逐维度打分**，
不是给一个笼统的总分。

## 背景

被测系统是一个企业内部知识库问答系统。它的硬性规则是：
1. 只能依据给定的资料回答，资料中没有的内容不得推测或补充
2. 每个事实性陈述后须标注来源编号
3. 资料不足时必须输出固定拒答句式
4. 涉及数字须原文照抄，不得换算或四舍五入

## 你将收到四段信息

- 用户问题：{{question}}
- 标准答案：{{expected_answer}}
- 系统实际检索到的资料：{{retrieved_context}}
- 系统实际生成的答案：{{actual_answer}}

## 你要评的四个维度

### 维度 1：忠实度 Faithfulness（0—1）

判定方法：**逐句检查**被测答案中的每一个事实性陈述，
判断它是否能在"系统实际检索到的资料"原文中找到依据。

- 所有事实性陈述都能找到依据 → 1.0
- 有 1 处找不到依据 → 0.5
- 有 2 处及以上找不到依据，或整体是编造的 → 0.0

⚠️ 注意：不要用"这个说法符合常识"作为依据。
   只认资料原文。资料里没写的就是没有依据。

### 维度 2：答案相关性 Answer Relevancy（0—1）

判定方法：被测答案是否回应了用户**真正在问**的问题。

- 完整、直接回应 → 1.0
- 部分回应（如只答了多子问题中的一个） → 0.5
- 答非所问、绕圈子、答了相邻但不同的问题 → 0.0

### 维度 3：完备性 Completeness（0—1）

判定方法：对照"标准答案"中标出的**必须包含要点**，计算覆盖率。

- 要点覆盖率 ≥ 90% → 1.0
- 60% ≤ 覆盖率 < 90% → 0.5
- 覆盖率 < 60% → 0.0

同时检查"不允许出现"的条目：**只要出现任何一条，本维度直接 0.0。**

### 维度 4：数字与事实精确性 Numeric Accuracy（0—1）

**本维度只对含数字、日期、金额的题生效；其他题返回 null。**

判定方法：逐个比对被测答案中的数字与资料原文。

- 全部一致，无四舍五入、无单位换算、无"约/大约/左右" → 1.0
- 有任何一处数字被改写、换算、模糊化 → 0.0

⚠️ 这是最容易被忽略的维度。特别注意：
   - "1204 万元" 写成 "约 1200 万元" → 0.0
   - "60 天" 写成 "两个月" → 0.0
   - "500 元/晚" 写成 "500 元左右" → 0.0

## 拒答题的特殊处理

如果标准答案中 `should_refuse = true`：

- 被测答案**恰好**为固定拒答句式，且未输出任何库外内容 → 四维度均为 1.0
- 被测答案拒答了，但附带了推测或常识补充 → 忠实度 0.0，相关性 0.5，其余 0.0
- 被测答案**没有拒答**（试图回答） → 四维度均为 0.0，并在 `critical_issue` 中标记
  `"must_refuse_but_answered"`

如果标准答案中 `should_refuse = false` 但被测系统拒答了：

- 四维度均为 0.0，并在 `critical_issue` 中标记 `"false_refuse"`
  （这是"误拒"，与"该拒未拒"同等严重）

## 输出格式（严格遵守，必须是合法 JSON）

```json
{
  "faithfulness": 0.0,
  "answer_relevancy": 0.0,
  "completeness": 0.0,
  "numeric_accuracy": null,
  "reasoning": "逐维度说明判分理由，每个维度一句话，必须引用具体内容",
  "critical_issue": null
}
```

`critical_issue` 取值为 null / "must_refuse_but_answered" / "false_refuse" /
"leaked_restricted_content"（出现越权内容）。

## 三条禁令

1. **不要给总分。** 只给出四个分维度分数。
2. **不要因为答案"读起来很专业"就给高分。** 只看是否符合资料。
3. **不要在 reasoning 里写"总体来说不错"这类空话。** 每一句都要指向具体内容。
```

## 二、为什么这个提示词要这样写（逐条解释）

| 写法 | 为什么 |
|------|--------|
| 要求"逐句检查" | 否则模型会整体印象打分，漏掉中间某句的编造 |
| 明确"不要用常识作为依据" | 模型天然倾向用世界知识补全，这恰好是我们要测的幻觉 |
| 反例里给了三个具体改写例子 | 模糊标准会得到随机分数；具体例子能显著提高一致性 |
| 拒答类单独处理并区分"该拒未拒"和"误拒" | 这两种错误方向相反，混在一起统计会让指标互相抵消 |
| 禁止给总分 | 只给总分无法定位问题 |
| 要求 critical_issue 字段 | 让"越权"这类严重问题能被程序自动筛出来，进入人工复核队列 |
| 要求引用具体内容 | 空泛的理由无法用于归因（是检索问题还是生成问题） |

## 三、人工校准方法（每轮评估必做）

1. 从 30—100 条结果中**随机抽 20—30 条**
2. 我自己按同样四个维度打分（不看裁判分数，避免锚定）
3. 计算偏差：

```
偏差 = 裁判判为"通过"但我判为"不通过"的条数 / 总抽查条数
```

4. 判断：

| 偏差 | 结论 | 动作 |
|------|------|------|
| < 10% | 裁判可信 | 继续用 |
| 10%—15% | 勉强可用 | 记录偏差，重写偏差最大的那个维度的评分标准 |
| > 15% | **裁判不可信** | 停用自动评分，先修评分标准；必要时改为人工评分 |

> **本项目当前状态**：偏差 8%，裁判可信。
> 上一次校准发现的问题：裁判对"多子问题只答一半"的判定偏松
> （给了 1.0 而人工判 0.5），已在维度 2 的判分规则里补充了"多子问题"的说明。

## 四、哪些题必须走人工评分（不交给裁判）

| 类型 | 示例 | 为什么 |
|------|------|--------|
| 权限判断 | Q019—Q021 | 是否越权必须人工确认，模型裁判可能"觉得答案很合理"就放过 |
| 涉及精确数字 | Q008、Q011、Q030 | 裁判容易忽略细微的数字错误 |
| 我自己也拿不准的 | Q027（时间错配） | 先人工定标准答案，再进评估集 |
| 主观题 | 无 | 本项目没有这类题 |

**处理方式**：在 `golden_set.yaml` 里给这类题加 `judge: human` 字段，
`run_eval.py` 遇到该字段则跳过裁判、输出待人工评分清单。

## 五、成本控制

裁判模型调用会消耗 Token。控制方式：

- 只对 `category in [normal, edge]` 的题跑自动裁判（约占 70%）
- `permission` 类用程序断言（检查响应体不含特定文档片段）→ 零成本、更可靠
- `refuse` 类用程序断言（检查答案是否恰好等于固定句式）→ 零成本，但需人工抽检

这样 30 条评估集的裁判调用只需约 21 次，成本可忽略。
**能用规则判断的，不要用模型判断**——这是省钱最快的办法。
