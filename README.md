# 企业知识库 RAG 平台 · 前置文档集（实例）

> **这是一个「填好内容的实例」，不是空模板。**
> 它把《企业级 RAG 知识库搭建系统》那份需求，按《AI Coding 大模型应用开发实战指南》
> 的七阶段方法论，转成 AI 编码工具可以直接消费的一组文档。
>
> 适用场景：**一个人 + AI 编码工具**，你懂 RAG 算法，不懂前后端。
> 原需求是按 5—8 人团队 + K8s + 微服务写的，本实例做了**单人化裁剪**，
> 裁剪点全部记录在 `docs/releases.md` 与 `docs/adr/` 里。

---

## 一、这套文档解决什么问题

AI 编码工具最大的风险不是"写不出代码"，而是**它不知道边界在哪里**——
于是它替你猜。猜错的部分会被写成几百行看起来很专业的代码，而且很难推翻。

这套文档就是"边界本身"。它把下面 6 类信息变成 AI 每轮都能读到的文件：

| 你担心的事 | 由哪份文件解决 |
|-----------|--------------|
| AI 擅自换技术栈、加框架 | `AGENTS.md` 第二节 + `docs/adr/` |
| AI 写出越权数据泄露 | `AGENTS.md` 硬规则 2/3 + `docs/data-model.md` |
| AI 编造答案、乱答 | `docs/spec.md` AC-03 + `evals/README.md` |
| AI 改坏了你无法察觉 | `AGENTS.md` 第四节 + `docs/quality-gates.md` |
| AI 把项目做成半成品（范围失控） | `docs/releases.md` 的"本期不做"清单 |
| 你分不清"改好了"还是"改坏了" | `evals/golden_set.yaml` + `docs/experiments/` |
| （V2）AI 用 SQL 查了不该查的数据 / 给了口径错的数字 | `AGENTS.md` 硬规则 17—21 + `config/semantic_layer.yaml` + `docs/text-to-sql.md` |

## 三、怎么用（按顺序，不要跳）

### 第 1 步：把 `rag-kb/` 整个复制成你的项目根目录

```bash
cp -r rag-kb ~/projects/corp-kb && cd ~/projects/corp-kb
git init && git add -A && git commit -m "chore: 初始化项目文档（阶段 0-1 产出）"
```

### 第 2 步：逐份把"实例内容"换成你的真实情况

每份文档里用 `> ⚙️ 待你确认` 标出的段落，是需要你替换的地方。
其余部分是已经推演好的内容，可以直接用。

**替换顺序（有依赖，不能乱）：**

| 顺序 | 文件 | 为什么这个顺序 | 你的投入 |
|------|------|--------------|---------|
| 1 | `docs/constraints.md` | 预算和合规决定后面一切 | 40 分钟 |
| 2 | `docs/spec.md` | 验收标准是全项目的靶子 | 2 小时 |
| 3 | `docs/releases.md` | 决定 V0.1 到底做到哪 | 1 小时 |
| 4 | `docs/glossary.md` | 术语一错，后面全错 | 30 分钟 |
| 5 | `docs/architecture.md` | 技术选型必须唯一 | 1.5 小时 |
| 6 | `docs/data-model.md` | 权限模型是地基，改起来最贵 | 1.5 小时 |
| 7 | `docs/adr/0001~0009` | 只确认"代价"和"复核条件"两栏 | 50 分钟 |
| 8 | `docs/openapi.yaml` | 冻结后前端后端才能并行 | 1 小时 |
| 9 | `docs/tasks.md` | 从这里开始取任务给 AI 做 | 1 小时 |
| 10 | `AGENTS.md` | 最后写，因为它汇总了前面所有硬约束 | 1 小时 |
| 11 | `evals/golden_set.yaml` | **你主导**，AI 只生成候选题目 | 6—10 小时 |
| 12 | `evals/README.md` | 及格线必须先定，不能事后调 | 1 小时 |
| 13 | `evals/attribution.md` | 只读一遍，知道"指标掉了先跑对照检索"即可 | 30 分钟 |

**总计约 19—23 小时。** 这 20 小时能省下的返工，经验值是 3—5 周。

> **（V2）如果你要做数据查询，前面这张表要加两步**，但**顺序不同**——
> 它必须排在 `architecture.md` 之后、`tasks.md` 之前，而且**先写语义层再写文档**：
>
> | 顺序 | 文件 | 为什么插在这里 | 你的投入 |
> |------|------|--------------|---------|
> | 5.5 | `config/semantic_layer.yaml` | **口径先于一切**。指标怎么算没定，后面的 SQL 全是猜 | 2—4 小时（**你主导**） |
> | 5.6 | `docs/text-to-sql.md` | 有了语义层，才能写清"哪些题走 SQL、哪些必须走文档" | 1 小时 |
>
> **不要跳过第 5.5 步直接做功能。** 这是这套文档里唯一一处"必须先有业务输入"的地方：
> 语义层写错了，系统会给出**执行成功、数字真实、但口径错**的答案——
> 它不会报错，只会让你在汇报时被问住。
> 详见 `docs/text-to-sql.md` 第零节（5 条前置条件）。

### 第 3 步：每次让 AI 干活，用同一句话开头

```
请先读 AGENTS.md 和 docs/tasks.md，然后实现 T____ 任务。做完停下等我确认。
```

> 用 **Trae** 开发的话，先看 `TRAE-启动手册.md`——它讲清了文档三层怎么摆、
> 规则怎么被自动加载、首日启动序列的 5 个提示词，以及 Trae 特有的 8 个坑。
> **最关键的一点**：Trae 不会自动读 `AGENTS.md`，它只自动读 `.trae/rules/`。

## 四、三条铁律（违反任何一条，这套文档就白做了）

1. **一次只让 AI 做一个任务。** 说"帮我实现检索模块"→ 它会一次改 15 个文件，
   你无法审查，出错也定位不到。说"实现 T05"→ 改动范围可控。

2. **评估集的标准答案必须你自己确认。**
   AI 可以出题、可以格式化，但"这个答案对不对""这个问题该不该拒答"
   必须你判断。让 AI 既出题又定答案 = 自己考自己。

3. **"本期不做"清单的效力等同于"本期要做"。**
   AI 天然倾向加功能。`docs/releases.md` 和 `docs/spec.md` 里的 `✗` 条目，
   是你以后拒绝它的唯一依据。

4. **"候选"与"结论"必须分开，结论只能由你确认。**
   系统产出的归因、分类、评分，一律只能叫**候选**；
   只有你确认过、且留下依据的才叫**结论**，才计入统计，才驱动优化方向。
   把它做成全自动的，你会按一个准确率 60% 的分组去修一个没坏的地方 ——
   而这件事**不会报错**，只会让你白干两周（`docs/adr/0008`、`evals/attribution.md`）。

## 五、这套文档与七阶段的对应关系

| 阶段 | 产出物 | 本实例对应文件 | 是否原需求已有 |
|------|-------|--------------|--------------|
| 0 需求与规格 | 用户故事、验收标准、边界清单 | `spec.md`、`releases.md` | 部分有（缺验收标准） |
| 1 架构与选型 | 架构图、ADR、接口契约 | `architecture.md`、`adr/`、`openapi.yaml` | 完全缺失 |
| 2 脚手架与规范 | AGENTS.md、可运行空壳 | `AGENTS.md`、`REPO_CONVENTION.md`、`Makefile` | 完全缺失 |
| 3 开发 | 任务清单 + 单任务循环 | `tasks.md` | 有功能列表（缺可验收任务） |
| 4 测试与评估 | 测试金字塔、Eval 三层 | `evals/`、`quality-gates.md` | 只有"要评估"，无指标体系 |
| 5 版本管理 | 提交规范、分支策略 | `REPO_CONVENTION.md` | 引用了但没有文件 |
| 6 部署与监控 | 流水线、监控、告警 | `ops-runbook.md` | 有模块清单（缺阈值与降级） |
| 7 迭代优化 | 实验记录 | `experiments/` | 完全缺失 |
